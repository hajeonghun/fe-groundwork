# fe-groundwork

프론트엔드 기반 지식을 **주제 단위로 파고들고, 실측하고, 판단 근거를 쌓는** 작업 공간.

> AI가 답을 주는 시대에 남는 것은 **그 답이 우리 상황에서 옳은지 판정하는 능력**이다.
> 판정하려면 근거가 필요하고, 근거는 원리·계측·도메인에서 나온다. 여기는 그 기초 공사를 하는 곳이다.

## 근거 문서 — `docs/`

| 파일 | 내용 |
|------|------|
| [`docs/AI-활용-학습법.md`](docs/AI-활용-학습법.md) | 학습 방법론. 5단계 사이클과 프롬프트 모음 |
| [`docs/프론트엔드-기반지식-학습맵.md`](docs/프론트엔드-기반지식-학습맵.md) | 36개 주제. 학습 지도, 더 깊게 팔 부분, 접목 지점, 자료 |

**여기 있는 `.md`가 마스터다.** `~/Documents/`의 `.docx`는 md에서 생성한 산출물이다.
Word로 볼 일이 있으면 `docs/README.md`의 변환 명령을 쓴다.

주제를 시작할 때 학습맵의 해당 항목을 열어놓고 `00-MAP.md`를 채운다.

## 이 프로젝트의 대원칙

**AI가 대신 쓴 문서를 쌓는 것이 목적이 아니다.**
AI 요약본을 폴더에 모으면 나중에 아무것도 안 남는다. 그럴 거면 이 프로젝트는 필요 없다.

그래서 파일마다 **주체를 명시**했다. 헷갈릴 때는 이 원칙으로 돌아온다.

| 표기 | 의미 |
|------|------|
| 🧑 **나** | 내가 직접 쓴다. AI에게 시키는 순간 학습이 사라지는 부분 |
| 🤖 **AI** | AI에게 맡긴다. 시간만 쓰고 배움은 없는 부분 |
| 🤝 **AI 검증** | 내가 먼저 쓰고, AI에게 반박·채점을 시킨다 |

**파일 개수가 6개인 이유** — 학습 사이클 5단계에 맞췄다. 순서대로 채우면 방법론이 저절로 지켜진다.

## 새 주제 시작하기

### 로드맵에 있는 주제 — 번호만

```bash

```

## 템플릿 두 종류

### `_template-experiment` — 실험형

**계측하거나 재현해서 눈으로 확인할 수 있는 주제.**
성능, 브라우저 런타임, 언어 동작 같은 것.

```
00-MAP.md            ① 얇은 지도            🤖 AI
01-QUESTIONS.md      ② 막힌 지점 = 내 구멍   🧑 나
02-SOURCES.md        ③ 1차 자료 확인         🤖 찾기 / 🧑 읽기
03-MEASUREMENTS.md   ④ 계측 조건과 수치      🧑 나
04-NOTES.md          ⑤ 내 언어로 정리        🧑 나 / 🤝 채점
05-APPLIED.md        ⑤ 실무 적용 기록        🧑 나
demo/                실험 코드              🤖 나쁜 버전 / 🧑 개선 버전
assets/              프로파일 스크린샷
```

### `_template-concept` — 개념형

**데모로 검증이 안 되고, 판단과 근거를 쌓아야 하는 주제.**
설계, 경계, 상태 소유권, API 설계, 도메인 지식 같은 것.

```
00-MAP.md            ① 얇은 지도            🤖 AI
01-QUESTIONS.md      ② 막힌 지점 = 내 구멍   🧑 나
02-SOURCES.md        ③ 1차 자료 확인         🤖 찾기 / 🧑 읽기
03-CASES.md          ④ 실제 코드베이스 사례   🧑 나
04-NOTES.md          ⑤ 내 언어로 정리        🧑 나 / 🤝 채점
05-DECISIONS.md      ⑤ 판단 기록             🧑 나
```

**실험형과 다른 곳은 두 군데다.**
`03-MEASUREMENTS` 대신 `03-CASES` — 계측 대신 **우리 코드베이스에서 이 원칙이 지켜지는지/깨지는지 찾는다.**
`05-APPLIED` 대신 `05-DECISIONS` — 적용 수치 대신 **왜 이렇게 결정했는지 근거를 남긴다.**

둘 다 "머리로만 이해한 것"을 "실물에 붙여본 것"으로 바꾸는 장치라는 점은 같다.

### 어느 쪽인지 헷갈릴 때

> **재현해서 수치나 화면으로 확인할 수 있는가?**
> 있다 → experiment / 없다 → concept

애매하면 experiment로 시작하고, 데모가 억지스러우면 `03-MEASUREMENTS.md`를 `03-CASES.md`로 바꾼다.
형식에 맞추려고 억지 데모를 만들지 않는다.

## 작업 순서

파일 번호가 곧 순서다. **번호를 건너뛰지 않는 것이 핵심이다.**

| 순서 | 파일 | 하는 일 | 흔한 실패 |
|------|------|---------|-----------|
| ① | `00-MAP.md` | AI에게 얇은 지도만 받는다 | **여기서 상세 설명까지 받아버리기.** 다 안 것 같아서 나머지를 안 하게 된다 |
| ② | `01-QUESTIONS.md` | 지도를 보고 스스로 설명해본다. 막히면 적는다 | 안 막혔다고 착각. 실제로 써보면 대부분 막힌다 |
| ③ | `02-SOURCES.md` | 막힌 것만 1차 자료로 확인 | 처음부터 원문 정독. 목적 없이 읽으면 안 남는다 |
| ④ | `03-MEASUREMENTS.md` / `03-CASES.md` | 직접 재현하거나 실제 사례를 찾는다 | 건너뛰기. **여기를 빼면 이 프로젝트를 할 이유가 없다** |
| ⑤ | `04-NOTES.md` | 내 언어로 정리하고 AI에게 반박시킨다 | AI 요약 붙여넣기 |
| ⑥ | `05-APPLIED.md` / `05-DECISIONS.md` | 실무에 적용하고 결과를 남긴다 | 데모만 하고 끝내기. 그러면 장난감이 된다 |

`04-NOTES.md`를 **마지막에서 두 번째에 쓰는 것**이 의도된 설계다.
정리를 먼저 하면 그건 AI 요약을 옮겨 적는 일이 되고, 아무것도 안 남는다.

### 단, `01-QUESTIONS.md`는 예외다

번호는 붙어 있지만 **한 번 하고 끝내는 단계가 아니라 계속 돌아오는 파일**이다.

```
00 → 01 → 02 → 03 → 04 → 05
      ↑     │    │    │
      └─────┴────┴────┘
        새 의문이 생길 때마다 계속 추가
```

처음부터 완벽한 질문 목록을 만들려고 붙잡고 있지 않는다.
**3~5개 나오면 그걸 들고 바로 `02`로 간다.** 나머지는 읽고 재현하는 과정에서 저절로 나온다.

## 완료 기준

주제 하나를 "끝냈다"고 말하려면 아래를 만족해야 한다.

- [ ] `01-QUESTIONS.md`에 적은 질문 중 핵심적인 것이 해소됐다 (전부일 필요는 없다)
- [ ] `03`에 **내가 직접 만든 수치나 사례**가 있다 (AI가 만들어준 것 말고)
- [ ] `04-NOTES.md`를 보지 않고 이 주제를 설명할 수 있다
- [ ] `05`에 실무 적용이 최소 1건 있다

**4개 중 3개 이하면 아직 ①단계에 머물러 있는 것이다.**

## 시작할 때 지킬 것

**세팅에 시간을 쓰지 않는다.** 빌드 도구, 정적 사이트 배포, 문서 자동화 — 전부 나중이다.
개발자가 학습 프로젝트에서 실패하는 가장 흔한 이유는 **인프라 만드는 게 재밌어서 정작 학습을 안 하는 것**이다.

첫 데모는 `demo/bad.html`을 브라우저로 여는 것으로 충분하다. 구조 개선은 3~4개 주제를 해본 뒤에 한다.
