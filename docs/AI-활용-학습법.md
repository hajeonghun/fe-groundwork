# AI를 활용한 기술 학습법

> 예전에는 크롬 렌더링 엔진 같은 주제를 배우려면 블로그 포스팅을 찾아 읽는 것 말고는 방법이 없었다.
> 이제는 AI에게 물어보면 되지만, **물어보는 방식이 잘못되면 예전보다 더 얕게 배우게 된다.**
> 이 문서는 그 함정을 피하고 AI로 깊이 있게 학습하기 위한 실전 방법론이다.

---

## 0. 전제: AI 학습의 가장 큰 함정

**"매끄러운 설명 = 이해"라는 착각.**

포스팅을 읽을 때는 이해 안 되는 부분에서 **막히는 감각**이 있었다. 문장이 어렵거나, 전제가 생략됐거나, 그림이 부족해서 멈추게 되고 — 그 멈춤이 "여기가 내가 모르는 지점"이라는 신호였다.

그런데 AI 답변은 항상 술술 읽힌다. 내 수준에 맞춰 다듬어져 나오기 때문에 **막히는 지점 자체가 사라진다.** 다 읽고 나면 이해한 것 같은데, 막상 설명해보라고 하면 한 문장도 못 쓴다.

그래서 방법론의 핵심 질문은 이것이다.

> ❌ 어떻게 하면 잘 물어볼까?
> ✅ **어떻게 하면 내가 모른다는 사실을 드러나게 만들까?**

아래 6가지 원칙은 전부 이 질문에 대한 답이다.

---

## 1. 지도는 얇게 받기 ⚠️

학습의 시작은 AI에게 전체 구조를 그리게 하는 것이 맞다. **순서를 바꾸는 것이지, 1차 자료를 버리는 것이 아니다.**

예전에 포스팅부터 읽었던 것은 그 방법밖에 없어서였지, 그것이 좋은 시작점이어서가 아니었다. 포스팅은 대부분 **지도가 아니라 지형의 일부**다. 필자가 관심 있는 부분만 깊게 파고, 전체 구조는 독자가 이미 안다고 전제한다. 그래서 처음 읽으면 "이 용어가 저 용어와 무슨 관계지?"를 계속 헤매게 된다.

AI는 그 반대를 잘한다. **전체 구조 + 용어 간 관계 + 경계선**을 내 수준에 맞춰 한 번에 그려준다.

### 함정: 지도 단계에서 상세 설명까지 받아버리는 것

**이 문서 전체에서 가장 자주 어긋나는 지점이다.**

①단계에서 친절한 상세 설명까지 받으면 거기서 학습이 끝난다. 다 이해한 것 같으니 ②~⑤로 넘어갈 동기가 사라진다. 그래서 ①은 **의도적으로 얕게** 끊어야 한다.

```
[주제]의 전체 흐름을 지도처럼만 그려줘.
- 단계 이름과 순서
- 각 단계에서 등장하는 핵심 용어와 그 용어끼리의 관계
- 이 주제의 경계 (어디까지가 이 주제이고 어디부터가 아닌지)

각 항목은 두 문장 이내로. 자세한 설명은 하지 마.
내가 나중에 뭘 파고들지 고르는 용도야.
```

목차 수준의 뼈대만 받고 곧바로 다음 단계로 넘어가, **뼈대에 살을 못 붙이는 지점**을 찾는다. 그 지점이 나와야 무엇을 읽을지가 정해진다.

### 1차 자료는 언제 보는가

- **③단계** — 막힌 지점이 정해진 뒤. 목적이 뾰족해서 원문 읽는 속도가 완전히 다르다. 문서 전체가 아니라 필요한 섹션만 본다.
- **①단계에서 예외적으로** — AI 설명이 애매하거나 버전에 따라 다를 것 같으면 그 자리에서 근거 링크만 받아두고, 읽는 것은 ③으로 미룬다.

> AI로 **지도**를 얻고, 내 설명으로 **구멍**을 찾고, 1차 자료로 **그 구멍만** 메운다.

## 2. 물어보지 말고, 나를 심문시키기

가장 효과가 큰 전환. 설명을 요청하는 대신 **역할을 뒤집는다.**

```
크롬 렌더링 파이프라인에 대해 나를 테스트해줘.
설명은 하지 말고, 내 답변의 허점만 지적하면서 한 번에 하나씩 질문해.
내가 틀리면 정답을 알려주지 말고, 반례가 되는 상황을 제시해줘.
```

"Layout → Paint → Composite 순서로 진행됩니다"를 읽으면 아무것도 남지 않는다.
하지만 **"`transform`은 왜 Layout을 건너뛰는가?"**를 직접 설명하려다 막히면, 그 지점이 내 진짜 구멍이다.

**핵심 포인트**

- AI가 답을 먼저 주지 못하게 명시적으로 막을 것 ("설명하지 마", "정답 알려주지 마")
- 한 번에 하나씩 질문하게 할 것 (한꺼번에 받으면 다시 수동적 읽기가 된다)
- 틀렸을 때 정답 대신 **반례**를 받으면 스스로 수정하게 되어 훨씬 오래 남는다

---

## 3. AI는 인덱스로, 근거는 1차 자료로

AI 답변을 **최종 지식이 아니라 검색 경로**로 취급한다.

특히 렌더링 엔진처럼 내부 구현이 계속 바뀌는 주제는 AI 지식이 오래됐거나, 여러 버전이 뭉개져 하나의 설명으로 합쳐져 있을 확률이 높다.

```
이 설명의 근거가 되는 Chromium 소스 파일 경로, 공식 문서,
설계 문서(design doc) 링크를 찾아줘. 내가 직접 읽고 확인하고 싶어.
```

AI 요약본만 읽었을 때와, 실제 `RenderingNG` 아키텍처 문서나 Chromium 소스
(`third_party/blink/renderer/core/`)까지 따라갔을 때는 **이해의 해상도가 완전히 다르다.**

**핵심 포인트**

- AI가 만든 요약은 "어디를 읽어야 하는지"를 알려주는 지도다. 목적지가 아니다.
- 근거 링크를 요구하는 것만으로도 AI가 확실하지 않은 부분을 스스로 드러낸다.
- 1차 자료: 공식 문서 > 설계 문서 > 소스 코드 > 스펙 문서 > 블로그 순으로 신뢰

---

## 4. 실물에 붙여서 확인하기 ⭐

**예전 학습 방식과 가장 크게 달라진 부분.**

크롬 렌더링이 좋은 예인 이유는, 지금은 브라우저를 직접 조작하고 계측할 수 있는 도구가 AI에 붙어 있다는 점이다. 개념 설명을 듣고 끝내지 말고 **바로 재현한다.**

**재현 예시**

- 일부러 레이아웃 스래싱을 일으키는 페이지를 만들고 Performance 탭 녹화
  → Recalculate Style / Layout이 프레임마다 반복되는 것을 눈으로 확인
- 같은 애니메이션을 `left` 버전과 `transform` 버전으로 만들어 프레임 타임 비교
- Layers 패널로 컴포지팅 레이어가 언제 생성되는지 확인
- `will-change`를 남발했을 때 메모리가 어떻게 늘어나는지 확인

"들은 개념"이 **"내가 그래프에서 직접 본 것"**이 되는 순간부터 안 잊힌다.

예전에는 실험 환경 세팅 비용 때문에 이 단계를 대부분 건너뛰었다. 지금은 AI에게 재현용 코드까지 만들게 하면 몇 분이면 된다. **AI로 절약한 시간을 여기에 몰아넣는 것이 가장 큰 이득이다.**

---

## 5. 잘못된 설명을 일부러 수집하기

```
크롬 렌더링 파이프라인에 대해 흔히 퍼져 있지만 틀렸거나
지금은 낡은 설명 5가지를 알려줘. 왜 틀렸는지도 함께.
```

블로그 포스팅 학습의 가장 큰 위험은 **오래된 정보를 그대로 받아들이는 것**이다.
이걸 뒤집어서 물어보면 오히려 지식의 경계선과 변화 이력을 알게 된다.

**변형 프롬프트**

- "이 주제에서 5년 전 설명과 지금 설명이 달라진 부분은?"
- "이 설명이 성립하지 않는 예외 상황은?"
- "이 개념을 잘못 적용해서 생기는 실제 버그 사례는?"

---

## 6. 출력으로 마무리 — 요약을 시키지 말고 내가 쓴다

**AI에게 요약을 시키면 기억에 남지 않는다.** 요약은 이해의 결과물이지 수단이 아니다.

내가 먼저 쓰고, AI에게 채점을 시킨다.

```
내가 이해한 걸 적어볼게. 사실 오류, 빠진 단계, 애매한 표현을 지적해줘.
칭찬은 빼고 틀린 것만 짚어줘.
```

**핵심 포인트**

- "칭찬은 빼고"를 반드시 넣을 것. 없으면 AI는 틀린 설명에도 우호적으로 반응한다.
- 글이 아니어도 된다. 다이어그램, 동료에게 하는 5분 설명, 커밋 메시지도 출력이다.
- 이 단계에서 막히면 2번(심문)으로 되돌아간다.

## 실전 루틴 (5단계 사이클)

| 단계 | 하는 일 | 누가 주도 |
|------|---------|-----------|
| ① 지도 그리기 | AI에게 전체 구조·용어·경계를 **얇게** 그리게 함 | AI |
| ② 구멍 찾기 | 내가 설명해보고 막히는 지점을 발견 | 나 |
| ③ 근거 확인 | 막힌 지점만 1차 자료로 파고듦 | 나 (AI는 인덱스) |
| ④ 실물 재현 | DevTools·코드로 직접 계측해서 확인 | 나 + AI 도구 |
| ⑤ 출력·검증 | 내 언어로 정리하고 AI에게 반박당함 | 나 |

**예전 방식과의 차이**

- ①과 ③의 **탐색 비용이 거의 0**이 되었다.
- 하지만 ②④⑤가 없어진 것은 아니다. 오히려 여기에 시간을 몰아넣어야 한다.
- AI만 쓰고 끝내는 학습은 ①에서 멈추는 것과 같다. 가장 흔한 실패 패턴.
- **①이 두꺼워질수록 ②로 넘어갈 확률이 낮아진다.** 지도를 얇게 유지하는 것이 나머지 단계를 살린다.

## 바로 쓰는 프롬프트 모음

### 지도 그리기 (얇게)

```
[주제]의 전체 흐름을 지도처럼만 그려줘.
- 단계 이름과 순서
- 각 단계의 핵심 용어와 용어끼리의 관계
- 이 주제의 경계

각 항목은 두 문장 이내로. 자세한 설명은 하지 마.
```

### 심문 모드

```
[주제]에 대해 나를 테스트해줘.
설명은 하지 말고, 내 답변의 허점만 지적하면서 한 번에 하나씩 질문해.
내가 틀리면 정답을 알려주지 말고 반례가 되는 상황을 제시해줘.
```

### 근거 추적

```
방금 설명의 근거가 되는 공식 문서, 설계 문서, 소스 파일 경로를 찾아줘.
확실하지 않은 부분은 "불확실"이라고 명시해줘.
```

### 오개념 수집

```
[주제]에 대해 흔히 퍼져 있지만 틀렸거나 지금은 낡은 설명 5가지와,
왜 틀렸는지를 알려줘.
```

### 재현 실험 설계

```
[개념]을 내 눈으로 확인할 수 있는 최소 재현 코드와,
어떤 도구의 어떤 지표를 봐야 하는지 알려줘.
설명보다 "직접 보고 확인하는 절차" 위주로.
```

### 채점 요청

```
내가 이해한 걸 적어볼게. 사실 오류, 빠진 단계, 애매한 표현을 지적해줘.
칭찬은 빼고 틀린 것만.

---
(내 설명)
```

### 깊이 조절

```
지금 설명을 세 단계로 나눠줘.
1) 실무에서 이 정도만 알면 되는 수준
2) 면접이나 설계 논의에서 필요한 수준
3) 엔진 내부를 이해하는 수준
지금은 2)까지만 자세히 설명해줘.
```

## 적용 예시: 크롬 렌더링 엔진

| 단계 | 구체적 행동 |
|------|-------------|
| ① 지도 | Parsing → Style → Layout → Paint → Composite 순서와 각 단계 용어만 목차 수준으로 (상세 설명은 받지 않음) |
| ② 구멍 | "`transform`은 왜 Layout을 건너뛰나?"를 직접 설명 시도 → 막힘 발견 |
| ③ 근거 | RenderingNG 아키텍처 문서, Blink 소스에서 컴포지팅 관련 코드 확인 |
| ④ 재현 | `left` vs `transform` 애니메이션 페이지 작성 → Performance 탭 프레임 타임 비교 |
| ⑤ 출력 | "리페인트와 리플로우의 차이"를 내 언어로 작성 → AI에게 반박 요청 |

## 체크리스트

학습을 마쳤다고 판단하기 전에 스스로 확인:

- [ ] AI의 도움 없이 이 개념을 화이트보드에 그려서 설명할 수 있는가?
- [ ] 이 개념이 **성립하지 않는** 예외 상황을 하나 이상 말할 수 있는가?
- [ ] 이 개념을 내 눈으로 직접 확인해본 적이 있는가? (계측·재현)
- [ ] 근거가 되는 1차 자료를 한 번이라도 열어봤는가?
- [ ] 내 언어로 쓴 설명이 남아 있는가? (AI 요약본 말고)

**5개 중 3개 이하면 아직 ①단계에 머물러 있는 것이다.**

## 한 줄 요약

> AI는 **탐색 비용을 0으로 만들어주는 도구**이지, **이해를 대신해주는 도구가 아니다.**
> 절약한 시간을 "직접 설명해보기"와 "직접 계측해보기"에 쓰는 사람만 예전보다 더 깊이 배운다.
