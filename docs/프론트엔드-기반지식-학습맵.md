# 프론트엔드 기반 지식 학습 지도

> 프레임워크 API는 2년이면 바뀌고 AI가 다 알려준다. 하지만 이 문서의 주제들은 10년 뒤에도 유효하고,
> **AI에게 물어볼 수 있어도 내 머릿속에 있어야 하는 종류**의 지식이다. 판단은 실시간으로 일어나기 때문이다.
> 리뷰 중에, 회의 중에, 장애 대응 중에.
>
> 학습의 목적이 **"구현하기"에서 "판정하기"로 이동**했을 뿐, 원리 학습이 필요 없어진 것이 아니다.
> 오히려 AI가 준 코드가 우리 상황에서 옳은지 판별하려면 더 필요해졌다.

각 주제는 네 가지로 정리했다.

- **알면 좋은 점** — 이걸 알면 어떤 판단이 가능해지는가
- **더 깊게 파면 좋은 부분** — 표면만 보면 놓치는 것들
- **접목해볼 수 있는 부분** — 실제 프로젝트에서 손댈 수 있는 지점
- **직접 확인하는 법 / 자료** — 계측 도구와 1차 자료

| 증상 | 원인 계층 | 주제 |
|------|-----------|------|
| 처음 뜨는 게 느리다 | 네트워크 | 6. HTTP·캐싱·CDN |

## 1. 브라우저 렌더링 파이프라인 / 컴포지팅 `티어 1`

**한 줄 정의** — HTML·CSS가 화면의 픽셀이 되기까지 거치는 단계와, 각 단계를 무엇이 다시 트리거하는가.

### 알면 좋은 점

- **"느리다"는 신고를 단계로 분해할 수 있다.** 스타일 계산인지, 레이아웃인지, 페인트인지, 합성인지. 분해되면 해결책이 자동으로 좁혀진다.
- **AI가 준 CSS·애니메이션 코드가 왜 끊기는지 판정할 수 있다.** AI는 `left`로 움직이는 애니메이션도 아무렇지 않게 준다. 돌아가긴 한다. 60fps가 아닐 뿐이다.
- **프레임 예산 감각이 생긴다.** 60fps = 프레임당 16.7ms. 이 숫자가 머릿속에 있으면 "이 정도면 되겠지"가 "이건 예산 초과"로 바뀐다.
- **Core Web Vitals를 지표가 아니라 원인으로 이해하게 된다.**

### 학습 지도 (얇게)

파싱(HTML→DOM, CSS→CSSOM) → 스타일 계산 → 레이아웃(리플로우) → 페인트 → 합성.
그리고 핵심 질문 하나: **어떤 CSS 속성이 어느 단계부터 다시 돌게 하는가.**
`width`·`top`은 레이아웃부터 전부, `background-color`는 페인트부터, `transform`·`opacity`는 합성만.
마지막으로 메인 스레드와 컴포지터 스레드의 분리.

### 더 깊게 파면 좋은 부분

- **레이아웃 스래싱(강제 동기 레이아웃)** — `offsetHeight` 같은 값을 읽는 순간 브라우저가 레이아웃을 즉시 계산해야 하는 이유. 읽기/쓰기를 섞으면 루프마다 레이아웃이 돈다. **실무에서 가장 자주 만나는 성능 버그.**
- **RenderingNG 아키텍처** — 현대 Blink의 실제 구조. 위 5단계는 교과서적 단순화다.
- **컴포지팅 레이어 생성 조건** — 언제 레이어가 생기고, `will-change` 남용이 왜 메모리를 잡아먹는가.
- **INP(Interaction to Next Paint)** — FID를 대체한 지표. 입력 후 다음 페인트까지라서 이벤트 루프 주제와 직접 연결된다.
- **CLS의 원인** — 크기 미지정 이미지, 늦게 삽입되는 배너, 웹폰트 교체.
- **`content-visibility`, `contain`** — 렌더링 작업을 통째로 건너뛰게 하는 선언. 긴 목록에서 효과가 크다.
- **가상 스크롤의 원리** — 라이브러리를 쓰더라도 왜 필요한지, 어떤 부작용(스크롤 점프, 접근성)이 있는지.

### 접목해볼 수 있는 부분

- 대량 데이터 그리드에 가상 스크롤 도입 판단, 행 높이 고정 여부 결정
- `content-visibility: auto`로 화면 밖 섹션 렌더링 스킵 — 긴 폼·리포트 화면에서 즉효
- 팀 규칙 정착 — "애니메이션은 `transform`/`opacity`만"
- 리스트 렌더링에서 읽기·쓰기 분리로 레이아웃 스래싱 제거
- 스켈레톤 UI로 자리를 미리 잡아 CLS 방지

### 직접 확인하는 법

| 도구 | 무엇을 보는가 |
|------|---------------|
| Performance 패널 녹화 | Recalculate Style / Layout / Paint가 프레임마다 반복되는지 |
| Rendering 탭 → Paint flashing | 어디가 다시 그려지는지 초록색 표시 |
| Rendering 탭 → Layer borders | 컴포지팅 레이어 경계 |
| Layers 패널 | 레이어 개수와 메모리 |

**추천 실험** — 같은 애니메이션을 `left` 버전과 `transform` 버전으로 만들어 프레임 타임을 비교한다. 설명 백 번보다 이 그래프 한 번이 오래 남는다.

**자료** — `web.dev` Rendering Performance / `developer.chrome.com` RenderingNG 시리즈, "Inside look at modern web browser"

## 2. 이벤트 루프, 태스크 vs 마이크로태스크 `티어 1`

**한 줄 정의** — 자바스크립트가 싱글 스레드에서 비동기 작업의 실행 순서를 정하는 규칙.

### 알면 좋은 점

- **비동기 코드의 실행 순서를 예측할 수 있다.** "왜 이 값이 아직 반영이 안 됐지" 류의 버그가 추측이 아니라 추론으로 풀린다.
- **UI가 멈추는 원인을 즉시 지목할 수 있다.** 메인 스레드를 누가 얼마나 잡고 있는지가 전부다.
- **AI가 준 비동기 코드를 검증할 수 있다.** AI는 `await`를 문법적으로 정확히 쓰지만, 그 코드가 메인 스레드를 50ms 잡는지는 신경 쓰지 않는다.
- **INP 개선의 이론적 근거가 된다.**

### 학습 지도 (얇게)

콜 스택 / 태스크 큐(매크로) / 마이크로태스크 큐의 세 가지 자리.
핵심 규칙은 하나 — **태스크 하나가 끝날 때마다 마이크로태스크 큐를 전부 비운다.**
렌더링은 태스크 사이에 끼어들고, `requestAnimationFrame`은 스타일·레이아웃 직전에 실행된다.

### 더 깊게 파면 좋은 부분

- **렌더링 스텝의 정확한 순서** — 태스크 → 마이크로태스크 전부 소진 → (필요 시) rAF → 스타일 → 레이아웃 → 페인트. 이걸 정확히 알면 "왜 rAF 안에서 DOM을 읽으면 안전한가"가 풀린다.
- **마이크로태스크 고갈** — 마이크로태스크가 자기 자신을 계속 큐잉하면 렌더링이 영영 오지 않는다.
- **Long Task와 INP의 관계** — 50ms 넘는 태스크가 왜 문제인가.
- **최신 스케줄링 API** — `scheduler.postTask()`, `scheduler.yield()`. 우선순위를 붙여 양보하는 방법.
- **React 동시성 렌더링** — 리액트 스케줄러가 이 메커니즘을 어떻게 이용해 렌더링을 쪼개는지. 프레임워크를 원리로 이해하게 되는 지점.
- **Node.js 이벤트 루프와의 차이** — phase 개념, `process.nextTick`. SSR·BFF를 만진다면 필요하다.

### 접목해볼 수 있는 부분

- 수만 건 데이터 가공을 청크로 쪼개고 중간에 양보해 UI 프리징 제거
- 입력 핸들러에서 무거운 작업을 분리해 INP 개선
- 스크롤 핸들러를 rAF 기반으로 전환
- 필수적이지 않은 초기화 작업을 유휴 시간으로 미루기
- 자동완성·검색에서 요청 취소와 응답 순서 보장

### 직접 확인하는 법

출력 순서를 **먼저 예측한 뒤** 실행해본다. 틀리면 그게 정확히 내 구멍이다.

```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
queueMicrotask(() => console.log('4'));
requestAnimationFrame(() => console.log('5'));
console.log('6');
```

Performance 패널 Main 트랙에서 Long Task(빨간 삼각형), Interactions 트랙에서 INP를 확인한다.

## 3. 메모리 관리와 누수 패턴 `티어 1`

**한 줄 정의** — 무엇이 언제 회수되고, 무엇이 왜 회수되지 않는가.

### 알면 좋은 점

- **업무용 SPA에서 특히 치명적이다.** 사용자가 브라우저를 하루 종일 켜두는 시스템이라면 누수는 반드시 드러난다. "오후만 되면 느려져요"의 정체가 대개 이것이다.
- **AI 코드에서 정리(cleanup) 누락을 잡아낼 수 있다.** AI는 리스너를 등록하는 코드는 잘 쓰지만 해제를 빠뜨리는 일이 잦다.
- **메모리와 프레임 드랍의 연결을 이해하게 된다.** 메모리 압박은 GC를 자주 부르고, GC는 메인 스레드를 멈춘다.
- **재현이 어려운 버그를 계측으로 잡는 경험이 생긴다.** 이 능력 자체가 팀에서 희소하다.

### 학습 지도 (얇게)

기준은 **참조 카운트가 아니라 도달 가능성**이다. 루트에서 닿을 수 있으면 살아남는다.
Mark and Sweep, 세대별 GC. 그리고 대표 누수 패턴 다섯 가지 — 리스너 미해제, 타이머 미정리, 분리된 DOM 참조, 전역 캐시 무한 증가, 클로저가 큰 스코프를 붙잡음.

### 더 깊게 파면 좋은 부분

- **3-스냅샷 기법** — 스냅샷 → 의심 작업 반복 → 스냅샷 → 비교. 누수 추적의 표준 절차. **이것 하나만 익혀도 실무에서 즉시 쓴다.**
- **Retainer 체인 읽기** — "무엇이 이 객체를 붙잡고 있는가"를 역추적하는 법. 처음엔 어렵지만 이게 핵심 기술이다.
- **Shallow size vs Retained size** — 진짜 범인을 찾으려면 후자를 봐야 한다.
- **`WeakMap`/`WeakSet`/`WeakRef`/`FinalizationRegistry`** — 언제 약한 참조가 정답이고 언제 과한 설계인지.
- **클로저의 스코프 공유** — 같은 스코프를 공유하는 함수가 하나라도 살아 있으면 스코프 전체가 남는다. 직관과 어긋나는 지점.
- **프레임워크별 누수 지점** — `useEffect` cleanup, 구독 해제, `AbortController`로 요청 취소.

### 접목해볼 수 있는 부분

- 화면을 여러 번 오갔을 때 메모리가 계단식으로 오르는지 확인
- 차트·에디터·그리드 라이브러리의 `destroy()`/`dispose()` 호출 여부 점검 — 서드파티에서 특히 자주 샌다
- 무한히 쌓이는 전역 캐시에 LRU나 개수 상한 도입
- 8시간 근무 패턴을 흉내 낸 장시간 세션 점검 루틴 만들기
- 리뷰 체크리스트에 "등록했으면 해제했는가" 명문화

### 직접 확인하는 법

Memory 패널의 Heap snapshot(비교), Allocation on timeline, Performance 패널의 JS Heap 그래프(톱니가 우상향하면 누수 신호), Detached elements 도구.

**추천 실험** — 특정 화면을 10번 열고 닫으며 3-스냅샷 기법을 적용한다. 대부분의 실제 프로젝트에서 뭔가 하나는 나온다.

**자료** — `developer.chrome.com` DevTools Memory 문서군 / V8 블로그 GC 포스트

## 4. 브라우저 저장소 `티어 2`

**한 줄 정의** — 쿠키, `localStorage`, `sessionStorage`, IndexedDB, Cache Storage 각각의 성격과 한계.

### 알면 좋은 점

- **"어디에 저장할까"를 근거로 정할 수 있다.** 대부분의 팀이 습관으로 `localStorage`를 쓰고 나중에 용량·동기 블로킹·보안 문제로 되돌아온다.
- **`localStorage`가 동기 API라는 사실의 무게를 알게 된다.** 메인 스레드를 막는다. 큰 데이터를 넣으면 그대로 렉이 된다.
- **인증 토큰 저장 위치 논쟁에 참여할 수 있다.** 이건 보안·인증 주제와 직결된다.

### 학습 지도 (얇게)

쿠키(서버 전송, 용량 작음, 만료·`HttpOnly`·`SameSite` 속성) / `localStorage`·`sessionStorage`(동기, 문자열, 약 5MB, 출처 단위) / IndexedDB(비동기, 대용량, 구조화 데이터, 트랜잭션) / Cache Storage(요청·응답 쌍, Service Worker와 함께).

### 더 깊게 파면 좋은 부분

- **저장소 할당량과 축출(eviction)** — 브라우저가 언제 데이터를 지우는가. `navigator.storage.estimate()`, `persist()`
- **IndexedDB의 실제 사용법** — 원시 API가 불편해서 대개 래퍼를 쓰지만, 트랜잭션 수명과 버전 업그레이드 흐름은 알아야 한다
- **탭 간 동기화** — `storage` 이벤트, `BroadcastChannel`. 업무 시스템에서 여러 탭을 띄우는 사용자는 항상 있다
- **`SameSite`와 서드파티 쿠키 종말** — 인증 흐름에 직접 영향
- **오프라인 우선 설계** — 로컬 우선 저장 후 동기화. 충돌 해결 전략
- **저장소별 보안 경계** — XSS 앞에서 `localStorage`가 무력한 이유

### 접목해볼 수 있는 부분

- 사용자 화면 설정(그리드 컬럼 순서·너비, 필터)의 저장 위치 재검토
- 임시 저장(작성 중인 폼) 기능을 IndexedDB로 구현
- 여러 탭 사용 시 로그아웃 동기화 처리
- 무거운 조회 결과의 클라이언트 캐싱과 만료 정책

**확인** — Application 패널에서 각 저장소 실물 확인, `navigator.storage.estimate()`로 할당량 조회
**자료** — MDN Storage API, `web.dev` Storage for the web

## 5. Web Worker와 오프스레드 처리 `티어 2`

**한 줄 정의** — 메인 스레드를 비우는 유일한 진짜 방법.

### 알면 좋은 점

- **"쪼개서 양보하기"의 한계를 넘는 카드를 갖게 된다.** 이벤트 루프 지식만으로는 결국 메인 스레드 안에서의 배분일 뿐이다.
- **무거운 기능을 포기하지 않아도 된다.** 대용량 엑셀 파싱, 암호화, 이미지 처리 같은 것.
- **비용도 알게 된다.** 데이터 전송(구조화 복제) 비용 때문에 작은 작업은 오히려 손해다.

### 학습 지도 (얇게)

Worker 생성과 `postMessage`, 구조화 복제 알고리즘, DOM 접근 불가라는 제약. `Transferable`로 복사 없이 넘기기. Comlink 같은 래퍼가 하는 일.

### 더 깊게 파면 좋은 부분

- **구조화 복제 vs Transferable vs SharedArrayBuffer** — 전송 비용의 세 단계
- **Worker 풀** — 매번 만들지 않고 재사용
- **모듈 워커와 번들러 통합** — 빌드 도구에서 워커를 어떻게 처리하는지
- **OffscreenCanvas** — 렌더링까지 워커로
- **Service Worker와의 구분** — 이름만 비슷하고 목적이 완전히 다르다
- **WASM과의 조합** — 계산 집약 작업

### 접목해볼 수 있는 부분

- 대용량 엑셀 파싱·생성을 워커로 이전
- 클라이언트 측 집계·정렬이 무거운 그리드
- 이미지 리사이즈·압축을 업로드 전에
- 검색 인덱싱, 대량 데이터 필터링

**확인** — Performance 패널에서 Worker 트랙이 별도로 표시되는지, 메인 스레드가 비는지
**자료** — MDN Web Workers API, `web.dev` "Use Web Workers to run JavaScript off the main thread"

## 6. HTTP/2·3, 캐싱 전략, CDN `티어 1`

**한 줄 정의** — 코드가 실행되기 전에 이미 결정되는 성능. 그리고 그것을 통제하는 헤더와 인프라.

### 알면 좋은 점

- **초기 로딩 성능의 대부분은 네트워크에서 결정된다.** 자바스크립트를 아무리 최적화해도 이 계층이 잘못돼 있으면 소용없다.
- **번들 분할 전략에 근거가 생긴다.** "청크를 몇 개로 쪼갤까"는 취향이 아니라 프로토콜과 캐시 정책의 함수다.
- **"왜 캐시가 안 먹지"를 헤더로 판별할 수 있다.** 배포했는데 옛 파일이 나가는 사고의 원인은 거의 항상 여기다.
- **인프라·백엔드와 같은 언어로 대화할 수 있다.** 6년차부터는 프론트 안에서만 해결되는 문제가 줄어든다.

### 학습 지도 (얇게)

HTTP/1.1의 한계(HOL 블로킹, 커넥션 제한) → HTTP/2(멀티플렉싱, 헤더 압축) → HTTP/3(QUIC, UDP 기반).
캐시 헤더 `Cache-Control`(`max-age`, `no-cache` vs `no-store`, `immutable`), `ETag`, `Last-Modified`.
강한 캐시(아예 안 감)와 조건부 요청(가서 304)의 차이. CDN의 엣지·오리진·무효화.

### 더 깊게 파면 좋은 부분

- **콘텐츠 해시 + `immutable` 전략** — 파일명에 해시를 넣고 1년 캐시, `index.html`만 `no-cache`. 현대 프론트엔드 배포의 표준형. **왜 이 조합인지 설명할 수 있어야 한다.**
- **`stale-while-revalidate` / `stale-if-error`** — 일단 옛 것을 주고 뒤에서 갱신. 체감 속도를 크게 바꾼다.
- **`Vary` 헤더의 함정** — 잘못 쓰면 캐시 적중률이 0이 된다.
- **HTTP/2에서 번들 전략이 달라지는 이유** — 파일이 많아도 예전만큼 나쁘지 않지만 압축률과 요청 오버헤드는 여전하다. 무조건 잘게 쪼개는 게 답이 아닌 이유.
- **리소스 힌트** — `preconnect`, `dns-prefetch`, `preload`, `prefetch`, `fetchpriority`. 각각 언제 쓰는지
- **Service Worker 캐싱 전략** — Cache First / Network First / SWR
- **CORS preflight 비용** — 왜 어떤 요청은 두 번 나가는가. 사내 시스템에서 의외로 자주 문제가 된다
- **압축** — gzip vs brotli

### 접목해볼 수 있는 부분

- 배포 캐싱 정책 정립 — 해시 자산 `immutable` + 엔트리 HTML `no-cache`
- 자주 안 바뀌는 코드성 데이터(공통 코드, 부서 목록)에 `ETag`나 SWR 적용
- 코드 스플리팅 단위 재검토
- 폰트 `preload` + `font-display: swap`
- 사내망·VPN 환경에서 요청 수 줄이기(지연이 대역폭보다 중요한 이유)

### 직접 확인하는 법

Network 패널의 Protocol 컬럼(h2/h3 확인, 기본 숨김이라 헤더 우클릭으로 추가), Timing 탭(TTFB), Size vs Transferred(캐시 적중), 그리고 `curl -I <url>`로 헤더 원문 확인.

**추천 실험** — 배포된 자산 하나를 `curl -I`로 찍어보고 정책이 의도대로인지 확인한다. 대부분의 팀에서 여기서 문제가 하나쯤 나온다.

**자료** — Ilya Grigorik *High Performance Browser Networking* (`hpbn.co` 무료 공개, 이 분야 표준 교재) / RFC 9110·9111·9114

## 7. 브라우저 보안 모델 `티어 1`

**한 줄 정의** — 브라우저가 무엇을 막아주고 무엇은 안 막아주는가.

### 알면 좋은 점

- **CORS 에러를 "백엔드가 헤더 열어주면 되는 것"이 아니라 정확히 이해하게 된다.** 왜 이 규칙이 존재하는지 알면 우회가 아니라 설계를 하게 된다.
- **XSS가 왜 프론트엔드의 책임인지 알게 된다.** 서버가 막아줄 수 없는 영역이 있다.
- **보안 리뷰·감사에 대응할 수 있다.** 금융·공공·업무 시스템일수록 이 대화가 자주 온다.
- **AI가 준 코드에서 위험 지점을 볼 수 있다.** `dangerouslySetInnerHTML`, 검증 없는 리다이렉트 같은 것.

### 학습 지도 (얇게)

동일 출처 정책(SOP)이 기본이고, CORS는 그 예외를 허용하는 장치다.
XSS(저장형·반사형·DOM 기반), CSRF와 `SameSite` 쿠키, 클릭재킹과 `X-Frame-Options`.
CSP로 실행 가능한 스크립트를 제한하는 방식.

### 더 깊게 파면 좋은 부분

- **preflight의 조건** — 어떤 요청이 단순 요청이고 어떤 게 preflight를 부르는가. `Content-Type`, 커스텀 헤더의 영향
- **CORS와 쿠키** — `credentials: 'include'`, 와일드카드 오리진 금지 규칙
- **CSP 실전** — `nonce`/`hash` 기반, `strict-dynamic`, Report-Only 모드로 점진 도입
- **DOM 기반 XSS** — 서버를 거치지 않는 XSS. 프론트엔드만의 문제
- **Trusted Types** — DOM XSS를 구조적으로 막는 최신 방어
- **의존성 공급망** — `npm audit`, lockfile 무결성, 서브리소스 무결성(SRI)
- **`postMessage` 검증** — `origin` 확인 누락은 흔한 실수
- **iframe 격리와 `sandbox` 속성** — 레거시 화면을 감쌀 때

### 접목해볼 수 있는 부분

- CSP를 Report-Only로 먼저 붙여 위반 로그 수집 후 점진 적용
- `dangerouslySetInnerHTML` / `v-html` 사용처 전수 조사 후 sanitize 적용
- 외부로 나가는 링크에 `rel="noopener noreferrer"` 점검
- 파일 업로드·다운로드 경로의 검증 흐름 확인
- 레거시 시스템 iframe 연동 구간의 `postMessage` origin 검증

**확인** — Console의 CORS·CSP 위반 메시지 정독, Security 패널, Network 패널의 preflight(OPTIONS) 요청 유무
**자료** — MDN CORS·CSP 문서 / OWASP Top 10, OWASP Cheat Sheet Series

## 8. 인증과 세션 `티어 1`

**한 줄 정의** — 누가 로그인했는지를 브라우저가 어떻게 기억하고 증명하는가.

### 알면 좋은 점

- **토큰 저장 위치 논쟁에 근거를 갖고 참여할 수 있다.** `localStorage` vs `HttpOnly` 쿠키는 취향이 아니라 위협 모델의 문제다.
- **토큰 만료 처리의 복잡성을 미리 안다.** 동시에 여러 요청이 401을 받았을 때 갱신을 한 번만 하도록 만드는 것 — 실무에서 반드시 만난다.
- **SSO·OAuth 연동에서 백엔드와 대화가 된다.** 사내 시스템은 대부분 통합 인증을 쓴다.

### 학습 지도 (얇게)

세션 쿠키 방식(서버가 상태를 가짐)과 토큰 방식(JWT, 서버가 무상태)의 근본 차이.
`HttpOnly`·`Secure`·`SameSite` 쿠키 속성. 액세스 토큰과 리프레시 토큰의 역할 분담.
OAuth 2.0의 인가 코드 흐름, OIDC가 그 위에 얹는 것.

### 더 깊게 파면 좋은 부분

- **PKCE** — 공개 클라이언트(SPA)에서 인가 코드 흐름을 안전하게 쓰는 방법. SPA라면 사실상 필수
- **토큰 갱신 경쟁 조건** — 동시 다발 401에서 갱신 요청을 하나로 모으는 큐잉·뮤텍스 패턴
- **JWT의 한계** — 즉시 무효화가 안 된다. 로그아웃·권한 회수를 어떻게 처리할 것인가
- **BFF 패턴** — 토큰을 브라우저에 두지 않고 서버가 대신 들고 있는 구조. 최근 권장되는 방향
- **자동 로그아웃과 세션 연장 UX** — 업무 시스템의 실제 요구사항
- **다중 탭 세션 동기화** — 한 탭에서 로그아웃하면 나머지도
- **권한(인가) 모델** — 인증과 인가의 구분, 화면·기능·데이터 단위 권한 설계

### 접목해볼 수 있는 부분

- 토큰 갱신 인터셉터를 경쟁 조건 안전하게 재작성
- 세션 만료 임박 안내와 연장 UX 개선
- 권한에 따른 화면·버튼 노출 규칙을 선언적으로 정리
- 로그인 상태 복원 흐름(새로고침 시 깜빡임) 정리

**자료** — OAuth 2.0 Security Best Current Practice / MDN 쿠키 문서 / `auth0.com` 블로그의 SPA 인증 시리즈

## 9. 실시간 통신 `티어 3`

**한 줄 정의** — 서버가 먼저 말을 걸어야 할 때의 선택지.

### 알면 좋은 점

- **필요 없는데 WebSocket을 도입하는 실수를 피한다.** 대부분의 "실시간"은 SSE나 폴링으로 충분하고 운영 비용이 훨씬 싸다.
- **연결이 끊긴다는 전제로 설계하게 된다.** 사내망·VPN 환경에서는 특히.

### 학습 지도 (얇게)

폴링 / 롱 폴링 / SSE(서버→클라 단방향, HTTP 기반, 자동 재연결 내장) / WebSocket(양방향, 별도 프로토콜).
선택 기준은 방향성과 빈도.

### 더 깊게 파면 좋은 부분

- **재연결 전략** — 지수 백오프, 지터. 서버가 죽었다 살아날 때 전체 클라이언트가 동시에 몰리는 문제
- **하트비트와 죽은 연결 감지** — 프록시·로드밸런서가 조용히 끊는 경우
- **끊긴 동안의 상태 복구** — 마지막 수신 지점부터 따라잡기(SSE의 `Last-Event-ID`)
- **메시지 순서와 중복** — 멱등성 처리
- **인프라 제약** — 로드밸런서 sticky session, 스케일아웃 시 브로드캐스트
- **탭이 백그라운드일 때** — 연결 유지 비용과 브라우저의 스로틀링

### 접목해볼 수 있는 부분

- 알림·결재 요청 같은 단방향 푸시를 SSE로 (WebSocket보다 단순)
- 대시보드 자동 갱신에서 폴링 주기와 서버 부하 균형 잡기
- 재연결 로직에 백오프·지터 적용

**자료** — MDN Server-sent events, WebSockets API / `web.dev` 관련 문서

## 10. JavaScript 코어 `티어 1`

**한 줄 정의** — 프레임워크를 걷어냈을 때 남는 언어 자체의 동작 원리.

### 알면 좋은 점

- **프레임워크의 동작을 마법이 아니라 코드로 이해하게 된다.** 6년차에서 갈리는 지점이다.
- **디버깅이 추론이 된다.** `this`가 왜 이거지, 왜 이 값이 캡처됐지 같은 것.
- **AI가 준 코드의 미묘한 오류를 잡는다.** 특히 클로저와 참조 관련.

### 학습 지도 (얇게)

실행 컨텍스트와 스코프 체인, 클로저, `this` 바인딩 규칙 네 가지, 프로토타입 체인, 값 vs 참조,
호이스팅과 TDZ, 이터레이터·제너레이터, 모듈(ESM)의 정적 구조.

### 더 깊게 파면 좋은 부분

- **클로저가 붙잡는 것의 실체** — 메모리 주제와 직결된다
- **프로토타입과 `class` 문법의 관계** — 클래스는 문법 설탕이라는 말의 정확한 의미
- **`Symbol`과 잘 알려진 심볼** — `Symbol.iterator`로 이터러블 만들기
- **Proxy와 Reflect** — Vue 반응성 시스템, MobX가 실제로 쓰는 기술. 원리로 이해하게 되는 지점
- **제너레이터와 비동기의 관계** — `async/await`가 어떻게 구현되는가
- **`Object.freeze`, 얕은 동결의 한계**
- **최신 문법의 실제 가치** — 옵셔널 체이닝, nullish 병합, `structuredClone`, `Array.prototype.at`

### 접목해볼 수 있는 부분

- 유틸리티 함수 라이브러리를 직접 만들며 클로저·커링 활용
- Proxy로 개발 환경 전용 디버깅 래퍼 만들기
- 반복이 많은 데이터 순회를 이터레이터로 지연 평가

## 11. 비동기 프로그래밍 패턴 `티어 1`

**한 줄 정의** — 실패하고, 늦고, 취소되고, 순서가 뒤바뀌는 세계를 다루는 법.

### 알면 좋은 점

- **네트워크가 불안정하다는 전제로 코드를 쓰게 된다.** 해피 패스만 있는 코드와 그렇지 않은 코드의 차이가 크다.
- **레이스 컨디션을 미리 본다.** 빠른 검색·자동완성에서 나중 요청이 먼저 도착하는 문제 같은 것.
- **AI 코드에서 가장 자주 빠지는 부분이 여기다.** 에러 처리, 취소, 정리.

### 학습 지도 (얇게)

Promise 조합자(`all`, `allSettled`, `race`, `any`)의 용도 구분.
`AbortController`로 취소. 에러 전파와 `try/catch`의 경계.
`await`의 직렬화 함정 — 반복문 안의 `await`는 순차 실행이다.

### 더 깊게 파면 좋은 부분

- **취소의 전파** — `AbortSignal`을 하위 함수까지 넘기는 설계, `AbortSignal.timeout()`
- **재시도 전략** — 지수 백오프, 어떤 에러가 재시도 가능한가(4xx vs 5xx), 멱등성 전제
- **중복 요청 제거(dedupe)와 인플라이트 공유** — 같은 요청이 동시에 여러 번 나가는 것 막기
- **레이스 방지** — 마지막 요청만 반영하는 패턴
- **에러 분류** — 네트워크 오류/비즈니스 오류/프로그래밍 오류를 구분해 다르게 처리
- **`unhandledrejection`** — 놓친 에러를 전역에서 잡기
- **비동기 상태 머신** — 로딩·성공·실패·재검증을 상태로 모델링

### 접목해볼 수 있는 부분

- API 클라이언트에 취소·재시도·중복 제거를 공통 계층으로 구현
- 자동완성·필터 검색의 레이스 컨디션 제거
- 폼 중복 제출 방지를 UI가 아니라 요청 계층에서
- 전역 에러 처리 정책 정리 (무엇을 토스트로, 무엇을 로깅만)

**자료** — MDN Promise·AbortController / `web.dev` "Fetch API" 관련 문서

## 12. TypeScript 타입 시스템 `티어 1`

**한 줄 정의** — 타입을 "붙이는 것"에서 "설계하는 것"으로.

### 알면 좋은 점

- **잘못된 상태를 표현 불가능하게 만들 수 있다.** 런타임 검증을 타입으로 대체하는 지점이 생긴다.
- **AI가 만든 타입의 허술함이 보인다.** AI는 `any`나 지나치게 느슨한 유니온을 쉽게 쓴다.
- **라이브러리 타입 정의를 읽을 수 있다.** 복잡한 제네릭 앞에서 멈추지 않게 된다.

### 학습 지도 (얇게)

구조적 타이핑(이름이 아니라 모양으로 판단), 유니온·인터섹션, 타입 좁히기(narrowing)와 타입 가드,
제네릭과 제약, `unknown` vs `any`, 리터럴 타입과 `as const`.

### 더 깊게 파면 좋은 부분

- **판별 유니온(discriminated union)** — 상태 모델링의 핵심 도구. "로딩 중인데 데이터가 있는" 불가능한 조합을 타입 수준에서 제거
- **조건부 타입과 `infer`** — 라이브러리 타입을 읽으려면 필요
- **매핑 타입과 키 리매핑** — `Partial`, `Pick` 같은 유틸리티가 실제로 어떻게 만들어지는가
- **변성(variance)** — 함수 매개변수의 반공변성, `strictFunctionTypes`
- **템플릿 리터럴 타입** — 문자열 조합을 타입으로
- **런타임 검증과의 연결** — Zod 등으로 스키마에서 타입을 도출. 외부 데이터의 경계를 어디에 둘 것인가
- **`satisfies` 연산자** — 넓히기를 막으면서 타입 검사만 받기
- **선언 병합과 모듈 보강** — 서드파티 타입 확장

### 접목해볼 수 있는 부분

- API 응답 타입을 스키마 검증과 연결해 경계에서 한 번만 검증
- 화면 상태를 판별 유니온으로 리팩터링해 불가능한 상태 제거
- 공통 컴포넌트의 props 타입을 제네릭으로 정교화
- `tsconfig`의 엄격성 옵션을 단계적으로 올리기

**자료** — TypeScript Handbook (공식) / *Effective TypeScript* (Dan Vanderkam) / `type-challenges` 저장소

## 13. 불변성과 참조 동등성 `티어 2`

**한 줄 정의** — 무엇이 "바뀌었다"고 판단되는가.

### 알면 좋은 점

- **리렌더링이 왜 일어나는지/안 일어나는지 설명할 수 있다.** React·Vue 성능 이슈의 절반이 여기서 나온다.
- **`useMemo`·`useCallback`을 감이 아니라 근거로 쓴다.** 남용도 문제고 누락도 문제다.
- **상태 업데이트 버그를 예방한다.** 직접 변형(mutation)이 만드는 조용한 버그.

### 학습 지도 (얇게)

값 타입과 참조 타입, 얕은 비교와 깊은 비교, 얕은 복사의 함정,
`Object.is`와 `===`의 차이, 불변 업데이트 패턴.

### 더 깊게 파면 좋은 부분

- **구조적 공유(structural sharing)** — 전체를 복사하지 않고 바뀐 경로만 새로 만드는 방식. Immer가 하는 일
- **자료구조 선택** — 배열 탐색 vs `Map`·`Set`. 목록이 커질 때 O(n²)가 되는 지점
- **정규화된 상태(normalized state)** — 중첩 대신 id 기반 평면 구조
- **깊은 복사의 실제 비용** — `structuredClone`, JSON 왕복의 한계(Date, undefined, 순환 참조)
- **메모이제이션의 비용** — 캐시도 메모리다. 언제 손해인가

### 접목해볼 수 있는 부분

- 불필요한 리렌더 추적 후 원인 제거 (React DevTools Profiler)
- 큰 목록 상태를 정규화 구조로 전환
- 반복 조회가 많은 배열을 `Map` 인덱스로 대체
- 상태 업데이트 로직에 Immer 도입 검토

**자료** — React 공식 문서의 상태 관리 섹션 / Immer 문서

## 14. CSS 레이아웃 엔진 `티어 1`

**한 줄 정의** — CSS가 "왜 이렇게 배치되는가"의 규칙. 감이 아니라 명세.

### 알면 좋은 점

- **CSS를 시행착오로 맞추는 시간이 사라진다.** 6년차인데도 이게 안 되는 경우가 흔하다.
- **AI가 준 CSS를 판정할 수 있다.** AI는 동작하는 CSS를 주지만 종종 불필요한 `!important`나 마법의 숫자를 포함한다.
- **디자인 시스템을 만들 수 있게 된다.** 규칙을 알아야 규칙을 만든다.

### 학습 지도 (얇게)

박스 모델과 `box-sizing`, 블록·인라인 서식 문맥(BFC), 마진 상쇄,
`position`의 기준(포함 블록), 쌓임 맥락(stacking context)과 `z-index`가 안 먹는 이유,
Flexbox 주축·교차축 모델, Grid의 트랙 기반 모델.

### 더 깊게 파면 좋은 부분

- **쌓임 맥락을 만드는 조건들** — `transform`, `opacity`, `filter`, `will-change` 등이 왜 `z-index`를 무력화하는가
- **포함 블록(containing block) 결정 규칙** — `position: fixed`가 `transform` 조상 안에서 이상하게 동작하는 이유
- **Flex의 `flex-basis`·`min-width: auto` 함정** — 넘치는 콘텐츠가 안 줄어드는 고전적 문제
- **Grid의 `minmax`, `auto-fit`/`auto-fill`, 서브그리드** — 복잡한 폼 레이아웃에 강력
- **컨테이너 쿼리** — 뷰포트가 아니라 컨테이너 기준. 컴포넌트 단위 반응형의 정답
- **캐스케이드 레이어(`@layer`)** — 우선순위 전쟁 종식. 레거시 CSS와 공존할 때 유용
- **논리 속성** — `margin-inline` 등. 국제화와 연결
- **CSS 변수의 런타임 성격** — 전처리기 변수와 근본적으로 다르다

### 접목해볼 수 있는 부분

- `z-index` 값을 토큰화하고 쌓임 맥락 정리
- 복잡한 폼·리포트 레이아웃을 Grid로 재작성
- 컨테이너 쿼리로 그리드·카드 컴포넌트의 반응형 재설계
- `@layer`로 레거시 CSS와 신규 스타일의 우선순위 정리
- 디자인 토큰(색·간격·타이포)을 CSS 변수로 체계화

**확인** — Elements 패널의 Computed 탭, Layout 탭(Grid/Flex 오버레이), Styles의 캐스케이드 확인
**자료** — MDN CSS 레이아웃 가이드 / `web.dev` Learn CSS / CSS 명세(정확한 규칙 확인 시)

## 15. 접근성 `티어 2`

**한 줄 정의** — 마우스 없이, 화면 없이도 쓸 수 있는가.

### 알면 좋은 점

- **업무 시스템에서는 생산성 문제다.** 종일 데이터를 입력하는 사용자는 키보드로만 움직인다. 접근성은 그 사람들의 속도다.
- **공공·금융 프로젝트에서는 법적 요구사항이다.** 국내에도 웹 접근성 인증 제도가 있다.
- **시맨틱 HTML을 다시 보게 된다.** `div`로 만든 버튼이 왜 문제인지 구체적으로 알게 된다.

### 학습 지도 (얇게)

시맨틱 요소가 기본으로 제공하는 것(포커스, 키보드 동작, 역할).
접근성 트리와 ARIA의 역할(보조하는 것이지 대체하는 게 아니다).
포커스 관리, 키보드 트랩, `tabindex` 사용 규칙, 대비율.

### 더 깊게 파면 좋은 부분

- **ARIA의 제1규칙** — 네이티브 요소로 되면 ARIA를 쓰지 마라
- **포커스 관리 패턴** — 모달 열림/닫힘, 라우팅 전환 시 포커스 이동, 포커스 트랩 구현
- **라이브 리전(`aria-live`)** — 비동기 결과·에러를 스크린리더에 알리기
- **복합 위젯 패턴** — 그리드, 트리, 콤보박스, 탭의 키보드 인터랙션 명세(ARIA Authoring Practices)
- **폼 접근성** — 레이블 연결, 에러 메시지 연결(`aria-describedby`), 필수 표시
- **대비율과 색 의존** — 색만으로 정보를 전달하지 않기
- **모션 민감성** — `prefers-reduced-motion`

### 접목해볼 수 있는 부분

- 데이터 그리드 키보드 내비게이션 구현 — 업무 시스템에서 체감 효과가 가장 큰 개선
- 모달·드로어의 포커스 트랩과 복귀 처리
- 공통 폼 컴포넌트의 레이블·에러 연결 표준화
- 자동화된 접근성 검사를 CI에 추가

**확인** — Lighthouse 접근성 감사, axe DevTools, Elements 패널의 Accessibility 탭, 키보드만으로 화면 완주해보기
**자료** — W3C ARIA Authoring Practices Guide (APG, 위젯 패턴의 표준) / MDN Accessibility / WCAG

## 16. 폼과 입력 처리 `티어 2`

**한 줄 정의** — 업무 시스템의 본체. 그리고 의외로 어려운 영역.

### 알면 좋은 점

- **ERP·업무 시스템은 사실상 폼 덩어리다.** 여기서의 숙련도가 곧 생산성이다.
- **한글 입력(IME)의 특수성을 알게 된다.** 조합 중 이벤트 처리를 모르면 검색·검증에서 계속 버그가 난다.
- **검증 로직의 위치를 설계할 수 있다.** 클라이언트·서버·타입 어디까지 할 것인가.

### 학습 지도 (얇게)

제어 컴포넌트와 비제어 컴포넌트의 트레이드오프, 네이티브 폼 검증(Constraint Validation API),
`input` vs `change` vs `blur` 이벤트, IME 조합 이벤트(`compositionstart`/`end`), `FormData`와 파일 업로드.

### 더 깊게 파면 좋은 부분

- **IME 조합 중 입력 처리** — 한글·일본어 입력에서 `input` 이벤트가 조합 중에도 발생한다. 실시간 검색·검증에서 반드시 처리해야 하는 지점
- **대형 폼의 성능** — 필드 수백 개짜리 폼에서 리렌더 범위 제어. 비제어 방식이 유리한 경우
- **검증 시점 설계** — 입력 중·블러·제출 중 언제 무엇을 보여줄 것인가(UX와 직결)
- **에러 메시지 연결과 포커스 이동** — 제출 실패 시 첫 에러 필드로
- **자동완성 속성** — `autocomplete`를 제대로 주면 사용자 입력 속도가 크게 는다
- **숫자·통화·날짜 입력** — 마스킹, 캐럿 위치 보존, 붙여넣기 처리
- **대용량 업로드** — 청크 분할, 진행률, 재개
- **이탈 방지** — `beforeunload`와 라우팅 가드

### 접목해볼 수 있는 부분

- 공통 폼 컴포넌트에 IME 안전 처리 내장
- 검색 입력의 디바운스를 조합 종료 기준으로 수정
- 대형 폼의 리렌더 범위를 필드 단위로 축소
- 숫자·금액 입력 컴포넌트의 캐럿·붙여넣기 처리 개선
- 작성 중 임시 저장(브라우저 저장소 주제와 연결)

**자료** — MDN Forms 가이드, Constraint Validation API / 각 폼 라이브러리(React Hook Form 등)의 설계 문서

## 17. 국제화와 로케일 `티어 3`

**한 줄 정의** — 언어만의 문제가 아니라 숫자·날짜·시간대·정렬의 문제.

### 알면 좋은 점

- **시간대 버그를 예방한다.** 날짜만 다루는 화면에서 하루가 밀리는 사고는 매우 흔하다.
- **번역이 문자열 치환이 아님을 안다.** 복수형, 어순, 문맥.
- **글로벌 대응 요구가 왔을 때 구조를 다시 안 짜도 된다.**

### 학습 지도 (얇게)

`Intl` API(`NumberFormat`, `DateTimeFormat`, `Collator`, `RelativeTimeFormat`, `PluralRules`),
UTC와 로컬 시간의 구분, 로케일 식별자, 번역 키 관리.

### 더 깊게 파면 좋은 부분

- **시간대 처리 원칙** — 저장은 UTC, 표시는 로컬. "날짜만" 값은 시간대를 붙이면 안 된다
- **`Temporal` API** — 기존 `Date`의 문제를 해결하는 새 표준. 도입 시점 판단
- **정렬(`Intl.Collator`)** — 한글·다국어 정렬은 코드 포인트 순이 아니다
- **복수형과 성별** — ICU 메시지 포맷
- **번들 분할** — 언어팩을 동적 로딩
- **양방향 텍스트(RTL)와 논리 속성** — CSS 주제와 연결

### 접목해볼 수 있는 부분

- 날짜·통화 포맷을 직접 만든 유틸에서 `Intl`로 교체
- 서버·클라이언트 시간대 처리 규칙 문서화
- 하드코딩된 문자열 추출과 키 체계 정리

**자료** — MDN `Intl` 문서 / `Temporal` 제안 문서

## 18. 모듈 시스템과 번들링 `티어 2`

**한 줄 정의** — 내가 쓴 코드가 사용자에게 도달하는 파일이 되기까지.

### 알면 좋은 점

- **번들 크기 문제를 원인부터 다룰 수 있다.** "무겁다"에서 "이 의존성이 트리셰이킹이 안 된다"로 정밀해진다.
- **코드 스플리팅 단위를 근거로 정한다.** 네트워크 주제와 함께 봐야 하는 부분.
- **빌드 에러를 이해한다.** ESM/CJS 혼용 문제는 지금도 매우 흔하다.

### 학습 지도 (얇게)

ESM과 CommonJS의 근본 차이(정적 vs 동적), 트리 셰이킹이 가능한 조건,
사이드 이펙트 선언(`sideEffects`), 동적 `import()`와 청크 분리, 번들러의 역할(해석·변환·묶기).

### 더 깊게 파면 좋은 부분

- **트리 셰이킹이 실패하는 이유** — 사이드 이펙트 추정, CJS 상호운용, 배럴 파일(`index.ts`에서 전부 재수출)의 함정
- **`package.json`의 `exports`·`main`·`module`** — 라이브러리가 어떤 형식을 노출하는가
- **청크 전략** — 벤더 분리, 공통 청크, 라우트 단위. 캐시 정책과 함께 결정해야 한다
- **의존성 크기 감사** — 무엇이 번들을 키우는가, 대체 가능한가
- **개발 서버의 원리** — 네이티브 ESM 기반 dev 서버(Vite)가 빠른 이유
- **모노레포 구조** — 워크스페이스, 빌드 캐시

### 접목해볼 수 있는 부분

- 번들 분석기로 상위 의존성 점검 후 교체·지연 로딩
- 배럴 파일 제거로 트리 셰이킹 개선
- 라우트 단위 코드 스플리팅 재정비
- 청크 분할 전략과 캐시 헤더 정책 정렬

**확인** — 번들 분석 도구(rollup-plugin-visualizer 등), Coverage 패널로 실제 사용되지 않는 코드 비율 측정
**자료** — 각 번들러 공식 문서 / `web.dev` "Reduce JavaScript payloads"

## 19. 트랜스파일과 브라우저 호환성 `티어 3`

**한 줄 정의** — 어디까지 지원할 것인가, 그 대가는 얼마인가.

### 알면 좋은 점

- **지원 범위가 번들 크기에 직접 영향을 준다는 걸 안다.** 사내 시스템에서 구형 브라우저 지원은 실제 비용이다.
- **"이 문법 써도 되나요"에 답할 수 있다.**

### 학습 지도 (얇게)

`browserslist`로 대상 정의, 트랜스파일(문법 변환)과 폴리필(기능 추가)의 구분,
`core-js`와 필요한 것만 넣기, Baseline 개념.

### 더 깊게 파면 좋은 부분

- **폴리필 전략** — 전역 오염 vs 격리, 필요한 브라우저에만 전달하는 방식
- **문법 다운레벨의 비용** — `async/await`나 클래스 필드 변환이 코드를 얼마나 부풀리는가
- **점진적 향상** — 기능 탐지(`@supports`, `if ('x' in y)`)로 최신 기능을 안전하게 쓰기
- **실사용자 브라우저 분포 확인** — 추측 대신 데이터로 지원 범위 정하기

### 접목해볼 수 있는 부분

- 실제 사용자 브라우저 통계를 근거로 `browserslist` 조정 후 번들 크기 비교
- 불필요한 폴리필 제거

**자료** — `browserslist` 문서 / `web.dev` Baseline / caniuse

## 20. 배포 전략 `티어 2`

**한 줄 정의** — 안전하게 내보내고, 문제가 생기면 빠르게 되돌리는 체계.

### 알면 좋은 점

- **배포가 이벤트가 아니라 일상이 된다.** 되돌릴 수 있으면 자주 배포할 수 있다.
- **캐시 사고를 구조적으로 막는다.** 네트워크 주제의 실전 적용면.
- **6년차부터 요구되는 역할이다.** 개인 기여자에서 팀의 흐름을 만드는 쪽으로.

### 학습 지도 (얇게)

CI/CD 파이프라인 구성, 환경 분리와 환경 변수 주입 시점(빌드 타임 vs 런타임),
정적 자산 배포와 캐시 무효화, 롤백 절차, 피처 플래그.

### 더 깊게 파면 좋은 부분

- **배포 중 청크 404 문제** — 사용자가 열어둔 구버전 페이지가 사라진 청크를 요청하는 고전적 사고. 구버전 자산 유예 보관과 재로딩 처리
- **점진적 배포** — 카나리, 블루-그린. 프론트엔드에서는 어떻게 하는가
- **피처 플래그** — 배포와 릴리스의 분리. 롤백보다 빠른 되돌림
- **빌드 재현성** — lockfile, 빌드 캐시
- **소스맵 배포 전략** — 공개할 것인가, 에러 추적 도구에만 올릴 것인가
- **프리뷰 환경** — PR마다 배포해서 리뷰

### 접목해볼 수 있는 부분

- 청크 404 대응 로직(새 버전 감지 후 새로고침 유도) 추가
- 캐시 무효화 정책 점검 및 배포 후 검증 자동화
- 피처 플래그 도입으로 위험한 변경의 릴리스 분리
- 롤백 절차 문서화 및 실제로 한 번 연습

**자료** — 각 CI 도구 문서 / Martin Fowler의 피처 토글 글

## 21. 관측성 `티어 2`

**한 줄 정의** — 내 화면에서 잘 돌아간다는 것 말고, 사용자에게서 실제로 어떤지 아는 것.

### 알면 좋은 점

- **"안 된다"는 신고에 데이터로 답할 수 있다.** 재현 안 되는 버그가 대부분인 업무 시스템에서 결정적이다.
- **성능 개선의 효과를 증명할 수 있다.** 개선했다는 주장과 수치는 다르다.
- **문제를 사용자보다 먼저 안다.**

### 학습 지도 (얇게)

에러 추적(전역 에러·`unhandledrejection` 수집, 소스맵 연결),
RUM(실사용자 성능 측정, Core Web Vitals 수집), 사용자 행동 로깅, 세션 재현 도구.

### 더 깊게 파면 좋은 부분

- **에러 그룹핑과 노이즈 제거** — 브라우저 확장·크롤러가 만드는 가짜 에러 걸러내기
- **소스맵 파이프라인** — 배포 시 업로드, 릴리스 버전 연결
- **필드 데이터 vs 랩 데이터** — Lighthouse 점수와 실사용자 지표가 다른 이유
- **분포로 보기** — 평균이 아니라 p75·p95. 소수의 느린 사용자가 진짜 문제다
- **에러 예산과 알림 임계값** — 알림 피로를 만들지 않는 설계
- **사용자 식별과 개인정보** — 무엇을 남기면 안 되는가

### 접목해볼 수 있는 부분

- 전역 에러 수집 도입 후 상위 에러부터 처리
- `web-vitals` 라이브러리로 실사용자 지표 수집 시작
- 성능 개선 작업의 전후 수치 비교 리포트 만들기 — **평가 근거로도 쓰인다**
- 주요 업무 흐름에 대한 성공/실패 로깅

**자료** — `web.dev` "Measure performance in the field", `web-vitals` 라이브러리 문서

## 22. 렌더링 전략 `티어 2`

**한 줄 정의** — HTML을 언제, 어디서 만들 것인가.

### 알면 좋은 점

- **프레임워크 선택의 근거가 생긴다.** Next.js를 쓰느냐가 아니라 왜 쓰느냐에 답할 수 있다.
- **사내 시스템에는 SSR이 불필요한 경우가 많다는 판단도 할 수 있다.** 유행이 아니라 요구사항으로 정하는 것.

### 학습 지도 (얇게)

CSR / SSR / SSG / ISR / 스트리밍 SSR의 차이와 각각의 트레이드오프(TTFB, 인터랙션 가능 시점, 서버 비용, 캐시 가능성).
하이드레이션이 무엇이고 왜 비싼가.

### 더 깊게 파면 좋은 부분

- **하이드레이션 비용과 대안** — 부분 하이드레이션, 아일랜드 아키텍처, resumability
- **React Server Components** — 서버·클라이언트 경계를 컴포넌트 단위로 긋는 모델. 무엇이 클라이언트로 넘어가고 무엇이 안 넘어가는가
- **스트리밍과 Suspense** — 느린 데이터가 전체를 막지 않게 하는 구조
- **SEO가 필요 없는 시스템에서의 판단** — 로그인 뒤의 업무 화면은 SSR 이득이 작다. 대신 초기 번들과 인증 흐름이 더 중요
- **엣지 렌더링** — 사용자 가까이서 렌더링하는 것의 실익

### 접목해볼 수 있는 부분

- 현재 프로젝트의 렌더링 전략을 요구사항 기준으로 재평가(문서로 남기기)
- 초기 로딩이 느린 화면에 스트리밍·지연 로딩 적용
- 공개 페이지와 로그인 후 화면에 서로 다른 전략 적용

**자료** — `web.dev` "Rendering on the Web" (Jason Miller, 이 주제의 기준 문서) / 각 프레임워크 공식 문서

## 23. 상태의 소유권 `티어 1`

**한 줄 정의** — 이 데이터의 진짜 주인은 서버인가 클라이언트인가.

### 알면 좋은 점

- **상태 관리 라이브러리 논쟁이 정리된다.** 도구 문제가 아니라 분류 문제였다는 걸 알게 된다.
- **캐시 무효화 전략을 설계할 수 있다.** 프론트엔드에서 가장 어려운 문제 중 하나.
- **AI가 절대 대신 못 하는 판단이다.** 우리 도메인의 데이터 신선도 요구를 모르기 때문이다.

### 학습 지도 (얇게)

서버 상태(원격이 진실, 비동기, 공유됨, 낡을 수 있음)와 클라이언트 상태(로컬이 진실, 동기)의 구분.
서버 상태에 필요한 것 — 캐싱, 재검증, 로딩·에러, 중복 제거.
URL도 상태 저장소라는 관점.

### 더 깊게 파면 좋은 부분

- **캐시 무효화 전략** — 시간 기반, 태그 기반, 수동. 무엇을 언제 다시 가져올 것인가
- **낙관적 업데이트와 롤백** — 실패 시 어떻게 되돌리는가, 그 사이 다른 변경이 있었다면
- **URL 상태 설계** — 필터·정렬·페이지를 쿼리스트링에 두면 공유·북마크·뒤로가기가 공짜로 해결된다. 업무 시스템에서 특히 유용
- **폼 상태의 위치** — 지역 상태 vs 전역
- **파생 상태를 저장하지 않기** — 계산 가능한 것을 상태로 두면 동기화 버그가 생긴다
- **여러 탭·사용자 간 정합성** — 다른 사람이 수정한 데이터를 보고 있을 때

### 접목해볼 수 있는 부분

- 전역 스토어에 있는 데이터를 서버/클라이언트로 재분류 — 대개 전역이 과하게 크다
- 목록 화면의 필터·정렬·페이지를 URL로 이전
- 서버 상태 라이브러리 도입 시 캐시 만료·재검증 정책을 데이터 종류별로 명시
- 낙관적 업데이트를 적용할 곳과 아닌 곳 구분

**자료** — TanStack Query 문서(개념 설명이 특히 좋다) / Kent C. Dodds "Application State Management"

## 24. 모듈 경계와 의존성 방향 `티어 2`

**한 줄 정의** — 무엇을 공통으로 올리고 무엇은 중복을 허용할 것인가.

### 알면 좋은 점

- **성급한 추상화를 피하게 된다.** 잘못된 공통화가 중복보다 비싸다는 걸 알게 된다.
- **코드베이스가 커져도 속도가 안 죽는 구조를 만들 수 있다.** 6년차에게 기대되는 역할.
- **AI가 만든 코드를 어디에 둘지 정할 수 있다.** 생성 속도가 빨라질수록 배치 기준이 중요해진다.

### 학습 지도 (얇게)

레이어드 구조와 기능(feature) 단위 구조, 의존성 방향 규칙(안쪽으로만),
공개 API(배럴)와 내부 구현의 구분, 순환 의존의 문제.

### 더 깊게 파면 좋은 부분

- **응집도와 결합도를 실제 판단 기준으로 쓰기** — "함께 바뀌는 것을 함께 둔다"
- **중복 허용 기준** — Rule of Three, 성급한 추상화의 비용
- **의존성 규칙 자동화** — ESLint 규칙이나 도구로 경계 위반을 빌드 시 차단
- **기능 단위 구조(FSD 등)** — 폴더 구조가 아니라 의존 규칙이 본질
- **모노레포 패키지 경계** — 언제 패키지로 분리할 가치가 있는가
- **마이크로 프론트엔드** — 대개 조직 문제의 해법이지 기술 문제의 해법이 아니다. 도입 비용을 정확히 알기

### 접목해볼 수 있는 부분

- 순환 의존 탐지 후 정리
- 공통 컴포넌트 폴더에서 실제로는 한 곳에서만 쓰는 것 골라내기
- 의존성 방향 규칙을 린트로 강제
- 새 기능의 폴더 구조 컨벤션 문서화

**자료** — *A Philosophy of Software Design* (John Ousterhout, 얇고 밀도 높다) / Feature-Sliced Design 문서

## 25. 컴포넌트 설계와 합성 `티어 2`

**한 줄 정의** — props가 열 개 넘어가기 전에 무엇을 해야 하는가.

### 알면 좋은 점

- **공통 컴포넌트가 괴물이 되는 걸 막는다.** `isXxx` 플래그가 계속 늘어나는 그 컴포넌트.
- **디자인 시스템을 만들 수 있게 된다.**
- **AI에게 컴포넌트를 시킬 때 기준을 줄 수 있다.** 기준이 없으면 AI는 요청받은 대로 플래그를 하나 더 추가한다.

### 학습 지도 (얇게)

합성(composition)과 설정(configuration)의 차이, `children`과 슬롯,
제어 vs 비제어 컴포넌트, 관심사 분리(로직 훅 / 표현 컴포넌트).

### 더 깊게 파면 좋은 부분

- **복합 컴포넌트(compound component) 패턴** — `Tabs`/`Tabs.List`/`Tabs.Panel` 식 API 설계
- **헤드리스 컴포넌트** — 동작과 스타일 분리. Radix·Headless UI가 하는 일
- **제어 반전** — 내부에서 다 처리하지 말고 사용자에게 결정권을 넘기기
- **props 설계 원칙** — 불가능한 조합을 타입으로 막기(타입 시스템 주제와 연결)
- **다형성 컴포넌트(`as` prop)** — 타입 정의가 까다로운 지점
- **컴포넌트 API의 하위 호환** — 공통 컴포넌트를 바꿀 때의 마이그레이션 비용

### 접목해볼 수 있는 부분

- props가 가장 많은 공통 컴포넌트를 합성 방식으로 재설계
- 그리드·모달·폼 필드 같은 핵심 컴포넌트를 헤드리스 구조로 분리
- 컴포넌트 사용 예시를 Storybook 등으로 문서화

**자료** — React 공식 문서의 컴포넌트 합성 섹션 / Radix UI, Headless UI 소스 읽기

## 26. 테스트 전략 `티어 2`

**한 줄 정의** — 무엇을 테스트하지 않을 것인가를 정하는 일.

### 알면 좋은 점

- **AI 시대에 중요도가 올라갔다.** 코드 생산이 빨라질수록 검증이 병목이 된다. 테스트는 AI 결과물의 안전망이다.
- **리팩터링을 두려워하지 않게 된다.**
- **커버리지 숫자의 무의미함을 알게 된다.** 무엇을 커버했는지가 중요하다.

### 학습 지도 (얇게)

테스트 피라미드(또는 트로피), 단위·통합·E2E의 역할 분담,
테스트 더블(mock/stub/spy)의 구분, 구현이 아니라 동작을 테스트한다는 원칙.

### 더 깊게 파면 좋은 부분

- **사용자 관점 쿼리** — 역할·레이블로 요소를 찾는 방식이 왜 좋은 테스트를 만드는가(접근성과도 연결)
- **네트워크 모킹** — MSW처럼 네트워크 계층에서 가로채기. 구현 결합을 줄인다
- **깨지기 쉬운 테스트의 원인** — 구현 세부에 결합된 테스트가 리팩터링을 방해한다
- **E2E의 비용 관리** — 느리고 불안정한 테스트를 어디까지 유지할 것인가, 플래키 테스트 대응
- **시각적 회귀 테스트** — 스크린샷 비교의 실효성과 유지 비용
- **AI 생성 코드의 테스트 전략** — 테스트를 먼저 쓰고 구현을 AI에게 맡기는 흐름

### 접목해볼 수 있는 부분

- 핵심 업무 흐름 2~3개만 E2E로 커버하고 나머지는 통합 테스트로
- 자주 깨지는 테스트를 골라 왜 깨지는지 분석
- 버그 수정 시 회귀 테스트 먼저 작성하는 습관화
- AI에게 구현을 맡길 때 테스트를 명세로 먼저 주기

**자료** — Kent C. Dodds "Testing JavaScript" 블로그 시리즈 / Testing Library 문서

## 27. 디버깅·프로파일링 방법론 `티어 1`

**한 줄 정의** — 도구 사용법이 아니라, 원인을 좁혀가는 절차.

### 알면 좋은 점

- **"측정할 줄 아는 사람이 판단을 독점한다."** 앞의 모든 성능 주제가 이 능력 위에서 작동한다.
- **추측 대신 증거로 말하게 된다.** 회의에서 결론이 빨라진다.
- **AI에게 좋은 컨텍스트를 줄 수 있다.** 증상만 던지는 것과 프로파일 결과를 주는 것은 답변 품질이 다르다.

### 학습 지도 (얇게)

이분 탐색으로 원인 좁히기, 재현 조건 최소화, 가설-검증 루프.
DevTools 전반 — Sources의 조건부 중단점·로그포인트, Performance, Memory, Network, Coverage.

### 더 깊게 파면 좋은 부분

- **`git bisect`** — 언제 깨졌는지 커밋 단위로 이분 탐색. 강력한데 덜 쓰인다
- **최소 재현 만들기** — 그 자체가 원인 규명이 되는 경우가 많다
- **Performance 패널 깊게 읽기** — 플레임 차트, Bottom-Up·Call Tree 탭의 차이, 셀프 타임과 총 시간
- **CPU 스로틀링·네트워크 스로틀링** — 실사용 환경 재현
- **원격 디버깅** — 실제 사용자 기기·모바일
- **프로덕션 디버깅** — 소스맵, 로깅 설계
- **로그포인트** — 코드 수정 없이 로그 심기

### 접목해볼 수 있는 부분

- 최근 어려웠던 버그를 되짚어 "어떤 절차였다면 더 빨랐을까" 정리
- 팀의 디버깅 노하우를 문서로 축적
- 성능 개선 작업을 반드시 전후 프로파일과 함께 기록

**자료** — Chrome DevTools 공식 문서 전체 훑기(의외로 모르는 기능이 많다)

## 28. 정적 분석과 코드 리뷰 `티어 3`

**한 줄 정의** — 사람이 볼 것과 기계가 볼 것을 나누는 일.

### 알면 좋은 점

- **리뷰에서 사소한 지적이 사라진다.** 포맷·컨벤션은 도구가 하고 사람은 설계를 본다.
- **AI 생성 코드가 늘어날수록 리뷰가 핵심 병목이 된다.** 리뷰 역량이 곧 팀의 처리량이다.

### 학습 지도 (얇게)

린터와 포매터의 역할 구분, 타입 검사와 린트의 경계,
커스텀 린트 규칙, 리뷰에서 무엇을 볼 것인가(설계·경계·예외 처리·테스트 가능성).

### 더 깊게 파면 좋은 부분

- **커스텀 ESLint 규칙 작성** — 팀 규칙을 문서가 아니라 코드로 강제. 반복되는 리뷰 지적을 규칙으로 승격
- **의존성 경계 강제** — 아키텍처 규칙을 린트로
- **리뷰 문화** — 무엇을 블로킹으로 볼 것인가, 제안과 요구의 구분
- **AI 코드 리뷰의 활용과 한계** — 무엇을 맡기고 무엇은 사람이 봐야 하는가

### 접목해볼 수 있는 부분

- 반복되는 리뷰 지적 세 가지를 린트 규칙으로 만들기
- 리뷰 체크리스트를 팀 문서로 명문화
- 정적 분석을 CI에 붙여 리뷰 부담 줄이기

**자료** — ESLint 공식 문서(커스텀 규칙 작성 포함) / Google Engineering Practices의 코드 리뷰 가이드

## 29. 시스템 설계 기초 `티어 2`

**한 줄 정의** — 프론트엔드도 분산 시스템의 한 노드라는 관점.

### 알면 좋은 점

- **"네트워크는 실패한다"를 전제로 설계하게 된다.** 재시도·타임아웃·중복 처리가 기본이 된다.
- **백엔드와 설계 대화가 된다.** 요구를 전달하는 것과 함께 설계하는 것의 차이.
- **장애 대응에서 원인 계층을 가른다.**

### 학습 지도 (얇게)

멱등성, 재시도와 백오프, 타임아웃, 캐시 계층(브라우저·CDN·서버·DB),
결과적 일관성, 낙관적/비관적 잠금.

### 더 깊게 파면 좋은 부분

- **멱등성 키** — 결제·주문 같은 중복 불가 작업에서 클라이언트가 해야 할 일
- **동시 편집 충돌** — 두 사용자가 같은 데이터를 수정할 때. 버전 필드, 충돌 감지, 사용자에게 어떻게 보여줄 것인가. **업무 시스템에서 실제로 자주 터지는 문제**
- **재시도 폭풍과 서킷 브레이커** — 클라이언트 재시도가 장애를 키우는 경로
- **캐시 일관성** — 여러 계층에 흩어진 캐시를 어떻게 무효화할 것인가
- **레이트 리밋 대응** — 429를 받았을 때의 클라이언트 동작
- **큐와 비동기 작업** — 오래 걸리는 작업의 진행 상태를 어떻게 보여줄 것인가

### 접목해볼 수 있는 부분

- 결제·저장 같은 중요한 요청에 멱등성 키 도입 논의
- 동시 수정 충돌 감지와 사용자 안내 흐름 설계
- 클라이언트 재시도 정책 정비(무한 재시도 제거)

**자료** — Martin Kleppmann *Designing Data-Intensive Applications* (범위는 넓지만 개념 정립에 좋다) / AWS Builders' Library의 타임아웃·재시도 글

## 30. API 설계와 데이터 모델링 `티어 2`

**한 줄 정의** — 화면이 아니라 데이터를 먼저 설계하는 습관.

### 알면 좋은 점

- **"이 API 이렇게 주세요"를 근거 있게 요청할 수 있다.** 프론트가 받아쓰기만 하면 결국 클라이언트가 복잡해진다.
- **화면 요구가 바뀌어도 안 무너지는 구조를 만든다.**
- **AI가 못 채우는 부분이다.** 우리 도메인의 관계를 알아야 모델링이 된다.

### 학습 지도 (얇게)

REST의 자원 모델링, 상태 코드와 에러 규약, 페이지네이션 방식(오프셋 vs 커서),
GraphQL의 트레이드오프, 버저닝, 스키마 우선 개발(OpenAPI).

### 더 깊게 파면 좋은 부분

- **에러 응답 규약** — 코드·메시지·필드 단위 오류를 어떻게 표준화할 것인가. 폼 검증과 직결
- **커서 페이지네이션** — 데이터가 실시간으로 바뀌는 목록에서 오프셋이 깨지는 이유
- **부분 응답과 과다 조회** — 화면마다 다른 필드 요구를 어떻게 다룰 것인가
- **BFF 패턴** — 화면 전용 API 계층을 프론트팀이 소유하는 구조
- **스키마에서 타입·클라이언트 자동 생성** — OpenAPI/GraphQL 코드 생성. 타입 시스템 주제와 연결
- **비즈니스 로직의 위치** — 무엇이 서버에 있어야 하는가(보안·일관성 기준)

### 접목해볼 수 있는 부분

- 에러 응답 규약을 백엔드와 합의하고 클라이언트 공통 처리 구현
- OpenAPI 스펙에서 타입·API 클라이언트 자동 생성 도입
- 목록 API를 커서 방식으로 전환 검토
- 화면 요구가 서버 모델을 오염시키는 지점 정리

**자료** — OpenAPI 명세 / Google API Design Guide / GraphQL 공식 문서의 Best Practices

## 31. 도메인 지식 `티어 1`

**한 줄 정의** — 기술 스택은 이직하면 리셋되지만 도메인은 누적된다.

### 알면 좋은 점

- **가장 저평가돼 있으면서 가장 큰 자산이다.** AI는 범용 코드를 무한히 만들어내지만 "이 회계 처리에서 마감 시점 조정이 왜 이렇게 동작해야 하는지"는 모른다.
- **코드 생산이 흔해질수록 "무엇을 만들어야 하는지 아는 사람"의 가치가 올라간다.**
- **요구사항의 오류를 먼저 발견하게 된다.** 이게 시니어의 실질적 정의에 가깝다.

### 학습 지도 (얇게)

담당 업무의 도메인 용어 사전 만들기, 실제 사용자의 하루 업무 흐름 파악,
법·제도적 제약(도메인에 따라 회계기준·개인정보보호 등), 데이터가 어디서 와서 어디로 가는지의 전체 흐름.

### 더 깊게 파면 좋은 부분

- **유비쿼터스 언어** — 코드의 이름과 현업의 용어를 일치시키기. 번역이 사라지면 버그도 준다
- **경계 컨텍스트** — 같은 단어가 부서마다 다른 뜻인 지점 찾기
- **실사용 관찰** — 사용자 옆에서 실제 작업을 지켜보기. 어떤 문서보다 정보량이 많다
- **엣지 케이스의 출처** — 예외 처리 대부분은 도메인 규칙에서 나온다
- **업무 흐름의 역사** — "왜 이렇게 돼 있는가"를 알면 함부로 바꾸지 않게 된다

### 접목해볼 수 있는 부분

- 담당 모듈의 도메인 용어집을 만들어 팀 문서화 — 신규 입사자 온보딩 자산이 된다
- 현업 담당자와 정기적으로 이야기하는 통로 만들기
- 코드의 변수·함수명을 현업 용어에 맞춰 정리
- 자주 나오는 문의·오류를 도메인 규칙 관점에서 분류

**자료** — 사내 업무 매뉴얼과 규정 문서(가장 중요한 1차 자료) / 현업 담당자 / *Domain-Driven Design Distilled* (Vaughn Vernon, 얇은 입문서)

# 파트 IX. 성능 심화

> 파트 I·II가 "왜 느린가"를 이해하는 원리라면, 여기는 **실제 개선 작업에서 효과가 가장 큰 축들**이다.
> 성능 개선의 성과는 대개 이 다섯 개에서 나온다. 원리는 판단을 위한 것이고, 이건 성과를 위한 것이다.

## 32. 성능 지표와 Core Web Vitals `티어 1`

**한 줄 정의** — 무엇을 재야 개선했다고 말할 수 있는가.

### 알면 좋은 점

- **지표 없이 개선은 불가능하다.** "빨라진 것 같다"와 "LCP p75가 3.1초에서 1.8초로 줄었다"는 완전히 다른 말이다. 후자만 예산과 시간을 받아낸다.
- **지표를 분해할 줄 알면 처방이 자동으로 나온다.** LCP가 느린 것과 LCP의 어느 구간이 느린 것은 다른 정보다. 대부분의 사람이 여기서 멈춘다.
- **랩 데이터와 필드 데이터의 괴리를 이해한다.** Lighthouse 90점인데 사용자는 느리다고 하는 상황을 설명할 수 있다.
- **업무 시스템에 맞는 자체 지표를 정의할 수 있다.** 로그인 뒤 화면에서는 LCP보다 "그리드에 데이터가 다 뜨는 시점"이 훨씬 중요하다.

### 학습 지도 (얇게)

Core Web Vitals 세 가지 — LCP(가장 큰 콘텐츠가 그려진 시점), CLS(예기치 않은 레이아웃 이동), INP(입력에 대한 응답성).
보조 지표 — TTFB, FCP, TBT.
랩 데이터(내 환경에서 측정)와 필드 데이터(실사용자)의 구분, 그리고 **평균이 아니라 p75**로 본다는 원칙.

### 더 깊게 파면 좋은 부분

- **LCP의 4단계 분해** — TTFB / 리소스 로드 지연 / 리소스 로드 시간 / 렌더 지연. **이 문서 전체에서 가장 실용적인 도구 하나를 꼽으라면 이것이다.** 어느 구간이 범인이냐에 따라 처방이 완전히 달라진다. 서버가 느린 것, 발견이 늦은 것, 파일이 큰 것, 렌더가 막힌 것은 각각 다른 문제다.
- **INP의 3단계 분해** — 입력 지연 / 처리 시간 / 프레젠테이션 지연. 이벤트 루프 주제와 직결된다.
- **프리로드 스캐너** — 브라우저가 HTML을 파싱하며 미리 리소스를 발견하는 메커니즘. JS로 삽입한 이미지가 늦게 발견되는 이유가 여기 있다. **LCP 개선에서 자주 놓치는 지점.**
- **Long Animation Frames(LoAF) API** — INP 원인을 스크립트 단위로 추적하는 최신 도구. 기존 Long Task보다 정보량이 많다.
- **Element Timing / User Timing API** — 자체 지표 정의. `performance.mark`/`measure`로 "그리드 렌더 완료" 같은 도메인 지표 만들기
- **CrUX(Chrome User Experience Report)** — 실제 사용자 데이터셋. 다만 사내 시스템은 데이터가 없을 수 있다
- **지표의 통계적 해석** — 평균이 왜 거짓말을 하는가, p75와 p95 중 무엇을 볼 것인가, 표본 수의 함정

### 접목해볼 수 있는 부분

- `web-vitals` 라이브러리로 실사용자 지표 수집 시작 — **성능 작업의 출발점이자 가장 먼저 할 일**
- 주요 업무 화면에 자체 지표 정의 (조회 버튼 클릭 → 그리드 렌더 완료까지)
- LCP를 4단계로 분해해 현재 병목 구간 특정
- 개선 작업마다 전후 지표를 기록하는 템플릿 만들기

### 직접 확인하는 법

| 도구 | 무엇을 보는가 |
|------|---------------|
| Lighthouse | 랩 데이터. 개선 방향 힌트 |
| PageSpeed Insights | 랩 + 필드(CrUX) 동시 확인 |
| Performance 패널 | LCP·CLS 마커, Layout Shift 원인 요소 |
| `web-vitals` 라이브러리 | 실사용자 지표를 직접 수집 |
| Performance Insights 패널 | LCP 단계 분해를 자동으로 보여줌 |

**추천 실험** — 주요 화면 하나를 골라 LCP를 4단계로 분해해본다. 대부분 예상과 다른 구간이 범인이다.

**자료** — `web.dev`의 Core Web Vitals 문서군 (특히 "Optimize LCP", "Optimize INP") / `web-vitals` 라이브러리 문서

## 33. 이미지와 미디어 최적화 `티어 1`

**한 줄 정의** — 전송량의 대부분이고, LCP 요소의 대부분이다.

### 알면 좋은 점

- **가장 적은 노력으로 가장 큰 성과가 나는 영역이다.** 자바스크립트 100KB 줄이는 것보다 이미지 하나 제대로 처리하는 게 빠를 때가 많다.
- **LCP 요소는 대개 이미지다.** 32번의 분해와 직접 연결된다.
- **CLS의 주요 원인이기도 하다.** 크기 미지정 이미지 하나가 지표를 망친다.

### 학습 지도 (얇게)

포맷 선택(AVIF > WebP > JPEG/PNG, 폴백 전략), 반응형 이미지(`srcset`/`sizes`),
`loading="lazy"`와 `decoding="async"`, `width`/`height` 지정으로 자리 예약,
`fetchpriority="high"`로 중요 이미지 우선순위 올리기.

### 더 깊게 파면 좋은 부분

- **LCP 이미지에 `loading="lazy"`를 붙이면 안 되는 이유** — 프리로드 스캐너가 발견을 못 한다. **매우 흔한 실수이고 효과도 크다.**
- **`<picture>`와 포맷 폴백** — 브라우저 지원에 따른 단계적 제공
- **이미지 CDN** — URL 파라미터로 리사이즈·포맷 변환. 원본 하나로 모든 경우를 커버
- **종횡비 예약** — `aspect-ratio`, `width`/`height` 속성이 CLS를 막는 원리
- **아이콘 전략 비교** — 인라인 SVG vs 스프라이트 vs 아이콘 폰트. 각각의 성능·접근성 트레이드오프
- **비디오** — `poster`, `preload` 값 선택, 자동재생 제약, 스트리밍 포맷
- **캔버스·차트 렌더링** — 데이터 시각화가 무거운 업무 화면에서의 최적화(오프스크린 렌더링, 다운샘플링)
- **업로드 전 클라이언트 리사이즈** — 사용자가 올리는 원본이 수 MB인 경우

### 접목해볼 수 있는 부분

- 주요 화면 이미지 전수 감사 — 포맷·크기·lazy 여부 점검
- LCP 이미지에 `fetchpriority="high"` + preload 적용, lazy 제거
- 모든 `<img>`에 `width`/`height` 부여해 CLS 제거
- 아이콘 시스템을 SVG 스프라이트로 통합
- 파일 업로드 시 클라이언트에서 리사이즈·압축 (Web Worker 주제와 연결)

**확인** — Network 패널을 Img로 필터링해 크기 정렬, Lighthouse의 이미지 관련 항목, Performance 패널에서 LCP 요소 확인
**자료** — `web.dev` "Optimize images", 반응형 이미지 가이드 / MDN `<picture>`·`srcset` 문서

## 34. 폰트 로딩 최적화 `티어 2`

**한 줄 정의** — 한국어 서비스에서 특히 무거운 문제.

### 알면 좋은 점

- **한글 폰트는 라틴 폰트와 차원이 다르다.** 글자 수가 수천 자라 파일이 크다. 영어권 자료의 조언이 그대로 적용되지 않는 대표적 영역이다.
- **텍스트가 안 보이거나 튀는 현상을 통제할 수 있다.** FOIT·FOUT는 선택의 문제지 사고가 아니다.
- **CLS의 숨은 원인이다.** 폰트가 교체되는 순간 글자 폭이 바뀌면서 레이아웃이 밀린다.

### 학습 지도 (얇게)

`font-display` 값들(`swap`, `optional`, `fallback`)의 차이, `preload`로 발견 시점 앞당기기,
`unicode-range`로 서브셋 분할, 시스템 폰트 스택이라는 선택지.

### 더 깊게 파면 좋은 부분

- **한글 서브셋과 유니코드 레인지 분할** — 자주 쓰는 글자를 앞쪽 파일에 모으고 나머지를 쪼개는 방식. Pretendard 같은 폰트가 실제로 이렇게 배포된다. 원리를 알면 사내 폰트에도 적용할 수 있다
- **`size-adjust`, `ascent-override`, `descent-override`** — 폴백 폰트의 메트릭을 웹폰트에 맞춰 교체 시 레이아웃 이동을 없애는 기법. **CLS 개선에 직접 효과**
- **FOIT vs FOUT 선택 기준** — 브랜드 일관성과 가독성 중 무엇이 우선인가. 업무 시스템은 대개 후자
- **가변 폰트** — 굵기별 파일을 여러 개 받는 대신 하나로
- **셀프 호스팅 vs 외부 CDN** — 서드파티 쿠키 정책과 캐시 파티셔닝 이후 외부 CDN의 이점이 줄었다
- **`font-display: optional`의 전략적 사용** — 첫 방문은 시스템 폰트, 이후 방문부터 웹폰트

### 접목해볼 수 있는 부분

- 현재 웹폰트의 실제 다운로드 크기 확인 후 서브셋 적용
- `font-display` 정책을 팀 차원에서 결정하고 문서화
- 폴백 폰트 메트릭 조정으로 폰트 교체 시 CLS 제거
- 사용하지 않는 굵기·스타일 제거

**확인** — Network 패널에서 폰트 파일 크기와 로드 시점, Performance 패널의 Layout Shift가 폰트 교체 시점과 겹치는지
**자료** — `web.dev` "Optimize web fonts" / MDN `@font-face` 문서

## 35. 서드파티 스크립트 관리 `티어 2`

**한 줄 정의** — 내 코드를 다 최적화해도 태그 하나가 전부 망칠 수 있다.

### 알면 좋은 점

- **통제 밖의 성능 저하를 통제 가능하게 만든다.** 분석 도구, 채팅 위젯, 태그 매니저는 대개 개발팀 결정이 아니지만 결과는 개발팀이 책임진다.
- **"우리 앱이 느린 게 아니다"를 데이터로 증명할 수 있다.** 이 근거가 있어야 제거·교체 논의가 시작된다.
- **장애 격리 관점도 얻는다.** 서드파티가 죽었을 때 우리 화면이 같이 멈추지 않게 하는 것.

### 학습 지도 (얇게)

스크립트 로딩 속성(`async` vs `defer` vs 모듈)의 정확한 차이,
서드파티가 메인 스레드를 점유하는 방식, 지연 로딩과 조건부 로딩.

### 더 깊게 파면 좋은 부분

- **Facade 패턴** — 무거운 위젯(채팅, 동영상 임베드) 대신 가벼운 껍데기를 먼저 그리고, 사용자가 상호작용할 때 실제 로드. 효과가 매우 크다
- **워커 오프로딩** — Partytown 같은 도구로 서드파티를 워커에서 실행
- **태그 매니저의 실제 비용** — 컨테이너 안에 뭐가 들어있는지 아무도 모르는 상태가 되기 쉽다
- **서드파티 예산 배정** — 전체 성능 예산 중 얼마를 외부에 내줄 것인가
- **실패 격리** — 서드파티 로드 실패가 우리 코드 실행을 막지 않게
- **개인정보·보안 관점** — 서드파티가 무엇을 수집하는가 (보안 주제와 연결)

### 접목해볼 수 있는 부분

- 현재 로드되는 서드파티 전수 목록화 + 각각의 메인 스레드 점유 시간 측정
- 사용하지 않는 스크립트 제거 (의외로 많다)
- 채팅·동영상 위젯에 Facade 적용
- 서드파티 로딩을 사용자 상호작용 이후로 지연

**확인** — Performance 패널에서 스크립트별 실행 시간(Bottom-Up), Lighthouse의 서드파티 사용량 항목, Network 패널에서 외부 도메인 필터링
**자료** — `web.dev` "Third-party JavaScript" 문서군 / Partytown 문서

## 36. 성능 예산과 회귀 방지 `티어 2`

**한 줄 정의** — 한 번 개선하는 것보다 유지하는 것이 어렵다.

### 알면 좋은 점

- **개선한 성능은 방치하면 3~6개월이면 원위치한다.** 기능은 계속 추가되고 의존성은 계속 늘어난다. 이걸 겪어본 사람과 아닌 사람의 접근이 다르다.
- **성능 작업을 이벤트가 아니라 프로세스로 만든다.** "성능 개선 스프린트"를 반복하는 대신 회귀를 막는 쪽이 훨씬 싸다.
- **팀을 설득하는 언어가 생긴다.** 개인의 노력에서 팀의 기준으로 옮기는 것 — 6년차 이후에 기대되는 역할이다.

### 학습 지도 (얇게)

성능 예산의 종류(번들 크기, 지표 임계값, 요청 수), CI 통합, 회귀 감지와 알림,
예산 초과 시의 처리 정책(경고인가 빌드 실패인가).

### 더 깊게 파면 좋은 부분

- **예산을 정하는 근거** — 임의의 숫자는 지켜지지 않는다. 실사용자 기기 분포, 네트워크 환경, 현재 수치의 소폭 개선치에서 출발
- **Lighthouse CI** — PR마다 자동 측정하고 임계값 위반 시 차단
- **번들 크기 회귀 추적** — 어떤 PR이 얼마를 늘렸는지 코멘트로 남기기
- **필드 지표 회귀 알림** — 랩 지표만 보면 실사용 저하를 놓친다
- **성능 작업 우선순위** — 영향도 × 사용자 수 ÷ 비용. 감이 아니라 계산으로
- **비즈니스 지표와 연결** — 이탈률·전환율·업무 처리 시간. 업무 시스템이면 "한 건 처리 시간"이 좋은 지표다
- **성능 문화** — 리뷰 체크리스트에 성능 항목 넣기, 정기 리포트

### 접목해볼 수 있는 부분

- 번들 크기 상한을 CI에 추가 (가장 쉽고 효과 확실한 첫걸음)
- 주요 화면에 Lighthouse CI 적용
- 성능 지표 대시보드를 만들어 팀에 공유
- 성능 개선 작업의 전후 수치를 리포트로 정리 — **평가 근거로도 쓰인다**
- 리뷰 체크리스트에 "이 변경이 초기 번들에 들어가는가" 추가

**자료** — `web.dev` "Performance budgets 101" / Lighthouse CI 문서 / bundlesize·size-limit 도구

# 부록 A. 어떻게 시작할 것인가

31개를 순서대로 다 하려 들면 아무것도 안 된다. 실제로 작동하는 방식은 이렇다.

**1) 지금 겪고 있는 문제와 가장 가까운 티어 1 주제 하나를 고른다.**
성능 신고가 들어와 있으면 1·2번, 인증 개편이 예정돼 있으면 8번. **문제가 있는 상태에서 배우는 것이 압도적으로 빠르다.**

**2) 「AI를 활용한 기술 학습법」의 5단계 사이클을 적용한다.**

| 사이클 | 이 문서에서 대응하는 것 |
|--------|------------------------|
| ① 지도 (얇게) | 각 주제의 **학습 지도** 섹션. 딱 이 수준까지만 AI에게 받는다 |
| ② 구멍 찾기 | **더 깊게 파면 좋은 부분**의 항목을 하나씩 스스로 설명해본다 |
| ③ 근거 확인 | 막힌 항목만 **자료**에서 찾아 읽는다 |
| ④ 실물 재현 | **직접 확인하는 법**의 실험을 그대로 실행한다 |
| ⑤ 출력·검증 | **접목해볼 수 있는 부분** 중 하나를 실제 코드에 적용하고 결과를 기록한다 |

**3) ⑤를 반드시 한다.**
읽어서 아는 것과 우리 프로젝트에 적용해본 것은 완전히 다른 자산이다. 접목 항목 하나를 실제로 처리하고 전후 수치를 남기면, 그게 학습 기록이자 팀 기여이자 평가 근거가 된다.

**4) 한 주제당 2~4주. 1년에 티어 1을 도는 것을 목표로.**
욕심내면 한 개도 안 남는다.

# 부록 C. 성능 특화 트랙

성능 측정·개선을 **주 무기로 삼겠다면**, 31개를 골고루 도는 대신 이 순서로 간다.
성능 관련 주제는 전체에 흩어져 있어서 순서를 따로 잡아주지 않으면 조각으로만 남는다.

## 학습 순서

### 1단계 — 측정의 기반 (여기부터 시작한다)

| 주제 | 왜 먼저인가 |
|------|-------------|
| 27. 디버깅·프로파일링 방법론 | 도구를 못 읽으면 나머지가 전부 추측이 된다 |
| 32. 성능 지표와 Core Web Vitals | 무엇을 재는지 모르면 개선을 증명할 수 없다 |
| 21. 관측성 | 내 PC가 아니라 실사용자에게서 재기 시작한다 |

**이 단계를 건너뛰고 최적화부터 하는 것이 가장 흔한 실패다.** 측정 없는 최적화는 운에 맡기는 것이고, 효과가 있었는지도 알 수 없다.

| 주제 | 핵심 |
|------|------|

| 주제 | 핵심 |

## 성능 개선 작업의 표준 루프

개별 작업은 매번 이 순서로 한다. 순서를 지키는 것 자체가 실력이다.

| 단계 | 하는 일 | 흔한 실수 |
|------|---------|-----------|
| ① 측정 | 현재 수치를 필드·랩 양쪽에서 기록 | 랩 데이터만 보고 판단 |
| ② 병목 특정 | 어느 계층·어느 구간인지 분해 (LCP 4단계 등) | 지표 하나만 보고 원인 추측 |
| ③ 가설 | "이걸 바꾸면 이 수치가 이만큼 줄 것" | 여러 개를 한꺼번에 바꿈 |
| ④ 개선 | 하나씩 적용 | 검증 없이 다음으로 |
| ⑤ 검증 | 같은 조건에서 다시 측정, 전후 비교 | 개선했다고 믿고 넘어감 |
| ⑥ 회귀 방지 | 예산·CI·모니터링에 반영 | 다음 분기에 원위치 |

**③에서 가설을 문장으로 적는 습관이 중요하다.** 적어두면 틀렸을 때 무엇을 잘못 이해했는지가 남는다. 그게 다음 번 판단의 재료가 된다.

## 성능 작업에서 흔한 함정

| 함정 | 왜 문제인가 |
|------|-------------|
| 측정 없이 최적화 | 효과 없는 작업에 시간을 쓰고, 효과가 있었는지도 모른다 |
| 랩 데이터만 신뢰 | Lighthouse 95점인데 사용자는 느릴 수 있다. 기기·네트워크·캐시 상태가 다르다 |
| 평균으로 보기 | 평균은 소수의 심각한 사용자를 숨긴다. p75·p95로 본다 |
| 개발 머신에서만 테스트 | 실사용자 기기는 훨씬 느리다. CPU 4~6배 스로틀링을 기본값으로 |
| 마이크로 최적화 | 루프 최적화보다 이미지 하나가 크다. 항상 큰 것부터 |
| 한 번에 여러 개 변경 | 무엇이 효과가 있었는지 알 수 없게 된다 |
| 개선 후 방치 | 회귀 방지가 없으면 반년 뒤 다시 같은 작업 |

## 첫 한 달에 할 일

성능을 본격적으로 파겠다면 순서는 이렇다.

1. **`web-vitals`로 실사용자 지표 수집을 시작한다.** 데이터가 쌓이는 데 시간이 걸리니 가장 먼저.
2. **주요 업무 화면 3개를 골라 자체 지표를 정의한다.** (조회 클릭 → 그리드 렌더 완료 등)
3. **그중 가장 느린 화면 하나의 LCP를 4단계로 분해한다.** 예상과 다른 곳이 범인일 확률이 높다.
4. **표준 루프대로 하나만 개선하고 전후 수치를 기록한다.**
5. **번들 크기 상한을 CI에 추가한다.** 가장 싸게 회귀를 막는 방법.

이 다섯 개를 마치면 **팀에서 성능을 데이터로 말할 수 있는 유일한 사람**이 된다. 그 시점부터 판단이 몰린다.

## 한 줄 요약

> 이 목록의 대부분은 **"왜 이렇게 동작하는가"에 답하기 위한 지식**이다.
> AI는 "무엇을 쓰면 되는가"에 답해주지만, **그 답이 우리 상황에서 옳은지는 판정해주지 못한다.**
> 판정할 수 있는 사람이 AI를 도구로 쓰고, 못 하는 사람은 AI를 쓸수록 부채를 쌓는다.
>
> 그리고 판단력을 따로 훈련하는 방법은 없다. 판단력은 **원리 + 계측 + 도메인**이 쌓인 결과로 나온다.
> 그래서 학습 대상은 여전히 구체적인 기술과 도메인이고, 바뀐 것은 학습의 목적뿐이다.
