# 렌더링 파이프라인 / 컴포지팅 — 실측

> **작성 주체: 🧑 나** (계측과 해석은 반드시 내가 한다)
> **언제:** 자료로 이해한 직후. 개념이 아직 흐릿할 때 재현하는 게 효과가 크다.
> **목적:** "들은 개념"을 **"내가 그래프에서 직접 본 것"**으로 바꾸기.
>
> ⚠️ **이 단계를 건너뛰면 이 프로젝트를 할 이유가 없다.**
> 예전에는 실험 환경 세팅 비용 때문에 대부분 건너뛰었지만, 지금은 AI에게 재현 코드를 시키면 몇 분이다.
> **AI로 절약한 시간을 여기에 몰아넣는 것이 이 방식의 전부다.**

## 지표를 고르는 법

**"뭘 측정하지"에서 막히는 경우가 많다.** 증상에서 거꾸로 고른다.

| 확인하려는 것 | 보는 지표 | 도구 |
|--------------|----------|------|
| 화면이 끊긴다 | FPS, 프레임당 소요 시간 | Performance 패널 / `watchFPS()` |
| 특정 동작이 느리다 | 구간 소요 시간(ms) | `measure()` / User Timing |
| 입력이 굼뜨다 | 입력 → 페인트 지연 | Performance 패널 Interactions |
| 메모리가 샌다 | JS Heap 크기 추이, 노드 수 | Memory 패널 스냅샷 비교 |
| 초기 로딩이 느리다 | LCP, TTFB, 전송량 | Network 패널 / Lighthouse |
| 메인 스레드가 막힌다 | Long Task 개수·길이 | Performance 패널 Main 트랙 |

**하나만 고른다.** 여러 지표를 동시에 보면 무엇이 원인인지 흐려진다.

## ⚠️ 차이가 안 나올 때

**가장 흔한 상황이고, 여기서 대부분 좌절한다. 하지만 실패가 아니다.**
순서대로 확인한다.

| # | 확인할 것 | 왜 |
|---|-----------|-----|
| 1 | **부하가 충분한가** | 요즘 브라우저는 웬만한 비효율을 그냥 처리한다. 반복 횟수를 10배, 100배 늘려본다. 요소 100개로 안 보이던 게 10,000개에서 보인다 |
| 2 | **CPU 스로틀링을 켰는가** | 개발 머신에서는 대부분의 문제가 안 보인다. 4~6배를 켠다 |
| 3 | **측정 지점이 맞는가** | 병목 구간을 안 감싸고 엉뚱한 데를 재고 있을 수 있다. Performance 패널로 먼저 어디가 오래 걸리는지 본 뒤 그 구간을 잰다 |
| 4 | **브라우저가 이미 최적화하고 있는가** | 예전엔 문제였지만 지금은 엔진이 알아서 처리하는 경우가 있다. **이건 매우 중요한 발견이다** — `02-SOURCES.md`의 "오개념 수집"에 적는다 |
| 5 | **가설 자체가 틀렸는가** | 내가 이해한 메커니즘이 실제와 달랐던 것. 가장 배울 게 많은 경우다 |

**4번이나 5번으로 결론이 나면 그 실험은 성공이다.**
"차이가 없었다"는 것도 결과이고, 오히려 **낡은 조언을 걸러낸 셈**이다. 아래 "해석"에 그렇게 적는다.

> 흔한 예 — 예전 자료에서 "이렇게 하면 느리다"고 하는데 지금 측정하면 차이가 없는 경우.
> 그럼 그 조언이 언제 왜 유효했고 지금은 왜 아닌지가 진짜 학습 내용이 된다.
