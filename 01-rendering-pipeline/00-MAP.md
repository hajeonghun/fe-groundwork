## 전체 흐름

크롬(Blink) 기준. 앞 단계의 출력이 뒤 단계의 입력이 된다.

| # | 단계 | 한 줄 |
|---|------|------|
| 1 | **Parse** | HTML을 DOM으로, CSS를 CSSOM으로 만든다. 여기까지는 "무엇이 있는지"만 안다. |
| 2 | **Style (Recalculate Style)** | 노드마다 최종 계산된 스타일 값을 확정한다. 어떤 선언이 이겼는지가 여기서 정해진다. |
| 3 | **Layout (Reflow)** | 각 요소의 위치와 크기를 계산한다. 이 결과를 뒤의 모든 단계가 참조한다. |
| 4 | **Pre-paint / Layerize** | 무엇을 별도 레이어로 뗄지, 변환·클립 같은 속성 트리를 정리한다. `transform`이 레이아웃을 건너뛰는 지점이 여기와 연결된다. |
| 5 | **Paint** | "어떻게 그릴지"의 명령 목록(디스플레이 리스트)을 만든다. 아직 픽셀은 하나도 안 나왔다. |
| 6 | **Raster** | 명령 목록을 실제 픽셀로 굽는다. 타일 단위로, 주로 메인 스레드 밖에서 일어난다. |
| 7 | **Composite / Draw** | 레이어들을 순서대로 겹쳐 한 프레임으로 합쳐 제출한다. 여기만 다시 도는 변경이 가장 싸다. |

옆으로 흐르는 축이 하나 더 있다 — **메인 스레드 → 컴포지터 스레드 → 래스터 스레드 → GPU 프로세스**.
어느 단계가 어느 스레드에서 도는지가 "부드러운 애니메이션"의 실제 기준선이다.

## 핵심 용어

| 용어 | 한 줄 설명 | 관련 용어 |
|------|-----------|----------|
| DOM / CSSOM | 파싱 결과로 만들어지는 두 개의 트리 | Parse, Style |
| Computed style | 한 노드에 대해 최종 확정된 스타일 값 | Style, 캐스케이드 |
| Reflow | Layout을 다시 도는 것. 이름만 다르다 | Layout, 무효화 |
| 무효화(Invalidation) | "이 부분 다시 계산해야 함"이라고 표시하는 것 | Style, Layout |
| 강제 동기 레이아웃 / 레이아웃 스래싱 | JS가 값을 읽어 레이아웃을 즉시 유발하고, 읽기·쓰기를 섞어 반복시키는 것 | Layout, 프레임 예산 |
| Display list (Paint record) | Paint가 만드는 그리기 명령 목록 | Paint, Raster |
| 합성 레이어(Layer) | 따로 래스터되어 나중에 합쳐지는 단위 | Layerize, Composite |
| Stacking context | 겹침 순서를 결정하는 단위. 레이어와 같은 말이 아니다 | z-index, Layer |
| `transform` / `opacity` / `will-change` | 어느 단계부터 다시 도는지를 바꾸는 대표 스위치 | Layerize, Composite |
| Tile | 래스터가 나눠 굽는 화면 조각 | Raster, 스크롤 |
| Compositor thread | 메인 스레드가 막혀도 스크롤·합성을 이어가는 스레드 | Composite, 오프스레드 |
| Commit / Activation | 메인 스레드의 결과를 컴포지터로 넘기고 반영하는 경계 | 스레드 축 |
| VSync / BeginFrame | 프레임이 시작되는 신호. 프레임 예산(60Hz면 약 16.7ms)의 기준점 | 프레임, rAF |
| rAF | 스타일·레이아웃 직전에 실행되는 콜백 | 이벤트 루프, 렌더링 스텝 |
| Viz (Display Compositor) | 브라우저 전체 화면을 최종 합성해 내보내는 곳 | GPU 프로세스 |

## 이 주제의 경계

- **여기부터** — DOM/CSSOM이 만들어진 시점부터 픽셀이 화면에 제출되기까지. "무엇을 그릴지"가 아니라 "어떻게 그려지는지"가 대상이다.
- **여기까지 아님(앞)** — 네트워크·리소스 로딩·파서 블로킹, JS 엔진 내부 실행은 다른 주제다. 파싱은 입구로만 다루고 파고들지 않는다.
- **여기까지 아님(뒤)** — GPU 드라이버, OS 컴포지터, 디스플레이 하드웨어 이후는 밖이다.
- **헷갈리는 인접 ① 이벤트 루프(2번)** — rAF·마이크로태스크·렌더링 스텝의 *타이밍*은 그쪽 주제고, 그 뒤에 실제로 무슨 일이 벌어지는지가 이 주제다.
- **헷갈리는 인접 ② Core Web Vitals(32번)** — 이 파이프라인을 *측정한 지표*이지 파이프라인 자체가 아니다.
- **헷갈리는 인접 ③ React의 "렌더링"** — 이름만 같고 층이 다르다. VDOM 계산은 위 표의 어느 단계도 아니다.
- **버전·엔진 주의** — 단계 이름과 레이어를 나누는 시점은 Blink/WebKit/Gecko가 다르고, Blink도 RenderingNG 이후로 바뀌었다. 오래된 자료의 "레이어 생성 조건" 목록은 지금 안 맞을 수 있다.

## 파고들 후보

- [ ] **레이아웃 스래싱(강제 동기 레이아웃)** — 읽기/쓰기를 섞으면 루프마다 레이아웃이 도는 이유. 실무에서 가장 자주 만나는 성능 버그.
- [ ] **RenderingNG 아키텍처** — 현대 Blink의 실제 구조. 교과서적 5단계는 단순화다.
- [ ] **컴포지팅 레이어 생성 조건** — 언제 레이어가 생기고, `will-change` 남용이 왜 메모리를 잡아먹는가.
- [ ] **INP(Interaction to Next Paint)** — FID를 대체한 지표. 입력 후 다음 페인트까지라서 이벤트 루프 주제와 직접 연결된다.
